# アーキテクチャの計測

## 要点

- 指標は目的から選ぶ。目的 → 問い → 指標の順に分解し、測りやすさではなく、判断や行動が変わるかで選ぶ
- 指標は、しきい値と実行の契機を決めて自動で回したときに、設計を守る仕組み（fitness function）になる
- 指標は組み合わせと推移で読み、チームの会話に使う。指標を目標にしたり、チーム同士の比較に使ったりすると歪む

*Software Architecture Metrics*（O'Reilly, 2022）の要約。10人の著者が1章ずつ書いた本で、扱う指標は配信の速さから保守性、事業の KPI まで幅広いが、根にある主張は共通している。問い別に整理した詳細と参照ページは[書籍ノート](research/reading-notes.md)に残している。

## 本の主張

1. **アーキテクチャの良し悪しは測って確かめる**。性能・可用性・保守性などの品質特性をめぐる判断はトレードオフを伴い、主観の議論で止まりやすい。一時点の測定は現在地を、時系列の測定は向かっている先を示す。（第7章）
2. **何を測るかは目的から決める**。GQM（Goal-Question-Metric）は goal → question → metric → data の木で、どのデータが何のためにあるかをたどれるようにする。組織 KPI → ドメイン KPI → 技術指標とつなぐ KPI Value Tree も同じ形をしている。（第6・10章）
3. **測るだけでなく、しきい値を決めて自動で回す**。ダッシュボードに並ぶだけの指標は、事後の証拠にとどまる。fitness function として CI や本番の監視で定期的に検証すると、設計の崩れを起きる前に止められる。（第2・8章）
4. **小さく始めて、段階的に締める**。安価なチェック（静的解析、循環依存の検査）から作り、既存のコードには緩いしきい値から入れる。ルールは5〜6個程度に絞り、使われなくなった測定は止める。（第2・7・9章）
5. **組み合わせと推移で読む**。デプロイ頻度だけ上げて変更失敗率が上がるのは、偏った改善である。一つの値は原因を示さないので、複数の指標を並べて推測し、振り返りで確かめる。（第1・5・6章）
6. **指標はチームの会話と行動のために使う**。定義と生データを公開し、ソフトウェアを届けるチーム自身が見る。指標を目標にすると（Goodhart's Law：指標は目標にした途端に良い指標でなくなる）、指標を満たすだけの改善に変わる。（第1・6・9章）
7. **測ろうとすると、設計の欠落が見える**。データの取り方を具体的に考えると、「負荷がないと記録が残らない」「リトライの責務が決まっていない」といった設計の穴が見つかる。（第10章）

## 各章の要約

- **第1章 four key metrics を使いこなす**（Andrew Harmel-Law）：デプロイ頻度・変更のリードタイム・変更失敗率・サービス復旧時間を、自分たちのパイプラインに合わせて定義する。集計は手作業、表示は wiki のダッシュボードから始めてよい。週次で指標を議論すると、チームが自ら改善を始め、やがてアーキテクチャの問題が表に出る。
- **第2章 fitness function テストピラミッド**（Rene Weiss）：fitness function を「指標＋文脈＋失敗条件」で定義し、6つの必須の分類で整理する。範囲（atomic／holistic）と契機（triggered／continual）の組み合わせでピラミッドの層が決まる。安価な下層を厚く、本番の業務指標を見る上層は少なく作る。
- **第3章 進化的アーキテクチャ**（Dave Farley）：将来は見通せない前提で、変更の余地を残す。modularity や結合度などの変えやすさの性質は、テストしやすさの条件と同じである。だから testability（テストのしやすさ）と deployability（独立したデプロイのしやすさ）を設計の指針にする。
- **第4章 Modularity Maturity Index**（Carola Lilienthal）：設計の負債の量を、modularity・hierarchy・pattern consistency の3原則から 0〜10 で評価する。8以上は良好、4〜8はリファクタリング、4未満は置き換えを検討する。
- **第5章 プライベートビルドと指標**（Christian Ciceri）：自動化を別チームに任せきると、本線が壊れても開発者が直せなくなる。push 前に手元で統合を確かめる private build に検証を戻す。状況は、フィードバックまでの時間、避けられた統合不具合の数、本線の復旧にかかった時間でつかむ。
- **第6章 組織のスケール**（João Rosa）：成長する組織では、アーキテクチャが組織の会話の形をなぞる（Conway's Law）。EventStorming でドメインの境界を見つけ、組織 KPI から技術指標までを KPI Value Tree でつなぐ。境界の引き直しは実験で確かめる。
- **第7章 測定の役割**（Eoin Woods）：測定を「成果物か稼働中か」×「チームの外から見えるか内側か」の4種に分ける。性能・スケーラビリティ・可用性・セキュリティごとに、測り方と落とし穴を示す。小さく始め、重要なものを測り、結果を見て行動する。
- **第8章 メトリクスからエンジニアリングへ**（Neal Ford）：指標は、客観的なしきい値を持つ fitness function として自動で実行されて初めて、エンジニアリングになる。例は、循環依存の検査、脆弱なライブラリの検出、新旧実装の結果比較（GitHub の Scientist）。
- **第9章 保守性のメトリクス**（Alexander von Zitzewitz）：保守性の最大の敵は構造の劣化で、特に循環依存の塊が育つこと。結合度・循環・サイズ・変更履歴の指標と推奨しきい値を示す。CI で毎日測り、推移を追う。
- **第10章 GQM**（Michael Keeling）：測りにくいものは goal → question → metric の木に分解する。外部 API の障害の事例では、GQM で指標を考える過程で設計の穴が見つかった。対策の後、9か月後に起きた14時間の停止を、利用者が気づく前に告知できた。

## ログ設計との関係

ログ・トレース・メトリクスは、第7章の分類では稼働中のシステムを測る手段にあたる。何を記録するかを「何に答えるための記録か」から決める[ログ設計の原則](../logging/principles.md)は、第10章の GQM と同じ形をしている。
