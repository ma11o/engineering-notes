# アーキテクチャの計測

## 要点

- 指標は目的から選ぶ。目的 → 問い → 指標 → データの順に分解すると、どのデータが何の判断に使われるかをたどれる
- 指標は、しきい値と実行の契機を決めて自動で回したときに、設計を守る仕組み（fitness function）になる
- 指標は一つの値で読まず、組み合わせと推移で読み、チームの会話と行動につなげる。指標を目標にすると歪む

このテーマは、*Software Architecture Metrics*（O'Reilly, 2022）を読んで、設計の良し悪しを確かめる指標の選び方と使い方を整理したもの。10人の著者がそれぞれ1章を書いた本なので、章ごとに独立して読める。

## 章をまたいで出てくる考え方

- **目的から指標へ**: 第10章の GQM（goal → question → metric）と、第6章の KPI Value Tree（組織 KPI → ドメイン KPI → 指標）は、どちらも目的から指標へ木の形で分解する
- **fitness function**: 第2・7・8・9章が共通して使う。指標にしきい値と実行の契機を付けて、品質特性が許容範囲にあるかを確かめる仕組み。第2章は分類と優先順位、第8章は自動化の意味、第9章は保守性のしきい値を扱う
- **組み合わせで読む**: 第1章の four key metrics（速さと安定性の2組）、第5章の3指標の組み合わせ表、第6章の mean time to discover と change fail rate の組み合わせ
- **小さく始めて締める**: 第2章（下層から作る）、第7章（行動につながる測定から始める）、第9章（緩い目標から段階的に締める）

## ログ設計との関係

ログ・トレース・メトリクスは、第7章の分類では稼働中のシステムを測る手段（operational measurement）にあたる。何を記録するかを「何に答えるための記録か」から決める[ログ設計の原則](../logging/principles.md)は、第10章の GQM と同じ形をしている。
