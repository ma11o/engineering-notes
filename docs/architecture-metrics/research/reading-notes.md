## 第1章 four key metrics を使いこなす

原題: *Four Key Metrics Unleashed*／著者: Andrew Harmel-Law

### 章の問い

*Accelerate* の four key metrics を、自分たちの配信の流れに合わせて定義し、集め、見せ、チームの改善の会話に使うにはどうするか。

### 本の記述

- four key metrics は、変更がバージョン管理に入ってから本番で動くまでを1本のパイプとして見るモデルから生まれる。デプロイ頻度と変更のリードタイムは開発のスループット、変更失敗率とサービス復旧時間はサービスの安定性を表す。［第1章 pp.2–3］
- 4つは組み合わせて見る。スループットを上げても安定性が下がれば、偏った改善で長続きしない。［第1章 p.3］
- 対象範囲（組織全体か、自分たちのプログラムか、インフラ変更を含むか）は4指標で揃える。インフラ変更をリードタイムに含めるなら、インフラ起因の障害も数える。［第1章 p.3］
- パイプラインの形は、単一のエンドツーエンド、成果物ごとの複数エンドツーエンド、サブパイプラインの連結、複数リポジトリが合流する fan-in の4種に分けて考える。後ろほど変更ごとの開始時刻をたどる処理が要る。［第1章 pp.4–8］
- 計測点は4つ。コミット時刻、本番デプロイ完了時刻、障害の検知（チケット起票）時刻、復旧（チケットクローズ）時刻。コミット時刻の代わりに main へのマージを起点にするのは妥協として許容する。［第1章 pp.6–9］
- 数えるのは、利用者に変更を届ける成功したデプロイだけ。途中で失敗したビルドを含めるとリードタイムが短く見える。時刻起動のビルドやバックアップ用のジョブは数えない。［第1章 p.8］
- 本番の障害は「利用者が目的の作業を完了できない、または続ける気をなくす状態」と定義する。見た目の不具合は含めず、離脱を招くほど遅い状態は含める。定義には判断が入るので、決めたら守る。［第1章 p.9］
- 復旧は根本原因の修正でなくてよい。ロールバックや自動フェイルオーバーで利用者に提供できる状態に戻れば時計を止める。本番がない場合は、本番に最も近い共有環境を本番として扱う。［第1章 pp.3, 9］
- 集計は手作業から始めてよい。デプロイ頻度は日ごとの成功数（0の日も含める）の直近31日平均、リードタイムは直近31日の平均、変更失敗率は直近31日の復旧済み失敗数÷デプロイ数、復旧時間は直近120日の平均または中央値。平均の平均は取らない。［第1章 pp.10–12］
- 変更失敗率は「1件の失敗は1回のデプロイが原因」と仮定する。未解決の失敗は4指標の一貫性のため計算から外すが、件数は隠さず表示する。［第1章 p.11］
- 生データ・計算・各指標の定義をすべて公開する。最初は wiki ページの minimal viable dashboard（現在値、定義と集計期間、過去の値、データの出所）で十分。［第1章 p.12］
- 主な読み手はソフトウェアを届けるチーム。経営層には集約した読み取り専用の値を見せ、詳細はチームに聞きに来てもらう。［第1章 p.13］
- 表示ではデプロイ数を他の指標のグラフに重ねるなど、繰り返し出る問いに答える文脈を足していった。［第1章 pp.13–17］
- 毎週、ADR とともに指標を議論すると、会話は「意味」→「なぜこの値か」→「どう改善するか」と進み、チームが自ら改善を始める。やがて結合の強さや観測しにくさなど、アーキテクチャの問題が表に出る。［第1章 pp.18–19］

### 用語

- four key metrics（DORA の4指標。デプロイ頻度、変更のリードタイム、変更失敗率、サービス復旧時間）
- instrumentation point（指標の元になる時刻を取る地点）
- fan-in pipeline（複数リポジトリのサブパイプラインが共有のパイプラインに合流する形）
- minimal viable dashboard（MVD。最小限の内容で始めるダッシュボード）
- ADR（Architecture Decision Record。設計判断の記録）

### 解釈・実務への示唆

- 指標の値だけでなく、対象範囲・何を1件と数えたか・集計期間を一緒に公開する。定義が見えないと、値の上下を議論できない。
- 計測点はパイプラインと障害チケットの時刻だけで、特別な仕組みは要らない。個人開発なら、本番デプロイが成功した時刻と、障害の issue を開いた・閉じた時刻から手作業で始められる（具体的な取得手順は未確認）。
- 本書の障害の定義（利用者が作業を終えられない状態）は、技術的なエラーではなく利用者から見た結果で数える点で、[レベル・結果・通知](../../logging/severity-and-outcomes.md)の考え方と同じ向きにある。

## 第2章 fitness function テストピラミッド

原題: *The Fitness Function Testing Pyramid: An Analogy for Architectural Tests and Metrics*／著者: Rene Weiss

### 章の問い

システムに合わせたアーキテクチャのメトリクスを、fitness function としてどう定義し、どう優先順位を付けて釣り合いの取れたテスト群にするか。

### 本の記述

- fitness function は *Building Evolutionary Architectures*（Ford, Parsons, Kua）の定義を借り、設計案が目標にどれだけ近いかをまとめる目的関数として扱う。出力は目標メトリクス（target metric）になる。検証は自動化が望ましいが必須ではない［第2章 pp.21–22］
- 概念の関係：fitness function が目標メトリクスと「fitness function context」（環境・定義・制約）を定義し、architectural test がメトリクスを生成してしきい値と照合する。前の3つは設計時に決め、テストは後から実装する［第2章 pp.22–23］
- 機能テストとの違いの例：顧客を1件作れるかは機能テスト、10件の作成が10ms以内に終わるかを測るのは architectural test［第2章 p.22］
- 例：単体テストのカバレッジ 90% 超を CI ビルドごとに検証、統合テストのカバレッジ 50% 超を夜間ビルドで検証。どちらも下回ればビルドを失敗させる［第2章 p.23］
- 例：外部 REST/JSON API に 10 秒の遅延を注入しても統合テストのエラーが 0% であること。変形として、実行時間が 10 分を超えたら失敗（遅延なしの通常は 5 分未満、つまり2倍まで許容）を加え、フォールバックの性能も確かめる［第2章 p.24］
- 必須の分類（6つ）：フィードバックの広さ（atomic／holistic）、実行トリガー（triggered／continual）、実行場所（CI/CD・テスト環境・本番）、メトリクスの型（真偽・離散値・時系列）、自動／手動、品質特性（quality attribute）。品質特性が最も重要と著者は述べる［第2章 pp.25–28, 30］
- 品質特性の例として ISO/IEC 25010 の8特性（機能適合性、性能効率性、互換性、使用性、信頼性、セキュリティ、保守性、移植性）とその副特性を挙げる。HP の FURPS という別の分類もある［第2章 pp.27–28］
- 任意の分類（4つ）：一時的／恒久的（例：長期リファクタリング中だけ置く）、静的／動的（例：オンライン利用者 1万〜10万人に応じて応答時間 50〜100ms の範囲を許す）、対象読者、適用範囲（サービスや技術ごと）［第2章 pp.29–30］
- 機能テストのピラミッド（下から単体、サービス／統合、E2E）は、実行時間・維持コストと得られる確信の釣り合いを取るためのモデル。上ほど遅く高価で、失敗原因の特定が難しい［第2章 pp.30–32］
- fitness function テストピラミッドの層は主に「広さ」と「トリガー」の組み合わせで決まる。下層は triggered atomic（カバレッジ、循環的複雑度、簡単な性能テスト）、中層は triggered holistic か continual atomic（夜間の統合テスト、本番での処理時間や画面表示時間の監視）、上層は holistic のみ（売上や checkout 率の監視、chaos engineering）［第2章 pp.32–35］
- 上層は現実の利用に最も近いが、作るのも維持するのも高価で、非決定的になりやすい。よって数を絞る。下層を広く取るのが基本だが、単体テストと違って下層も無制限に増やすべきではない（それぞれ負担を生むため）。文脈によってはピラミッドが逆になることもある［第2章 pp.33–35］
- 上層の例：時間帯ごとの1分あたり売上の下限（例：深夜 €200、夕方 €1500 など）を本番で常時検証する動的な holistic 関数。もう一つは、夜1時のローリングデプロイ中にログイン〜checkout の主要5ユースケースを流し続け、100ms 以内に応答することを確かめる（ゼロダウンタイムの確認）［第2章 pp.37–39］
- 分類は白黒はっきり付かないことも多い。分類の目的は、重要な観点のカタログとして使うことと、まだ手薄な領域を見つけることにある［第2章 p.39］
- 作り方の7手順：(1) 主要なステークホルダーと品質目標を合意し文書化、(2) fitness function の下書きを共有リスト／バックログに置く、(3) 重要で今実現できるものを選ぶ（初回はピラミッド下層から）、(4) 定義と層の分類を確定、(5) メトリクスを出す自動テストを作る、(6) ダッシュボードで可視化、(7) 定期的に見直し、価値のないものは廃止し、しきい値を厳しく／緩くする［第2章 pp.39–41］
- 著者は Ford らの「最初に fitness function を特定する」主張に概ね賛成しつつ、要件と同じく最初から全部は分からないので、小さく始めて学びながら追加することを勧める。簡単だからという理由で目標と無関係なテストを自動化するのは典型的な失敗とする［第2章 p.40］

### 用語

- fitness function（設計が目標にどれだけ近いかをまとめる目的関数）
- target metric（fitness function が達成・改善を目指す値）
- fitness function context（実行環境・定義・制約など、メトリクスの前提となる情報）
- architectural test／architectural verification（機能でなく品質目標を検証するテスト）
- atomic／holistic（システムの一部だけを見るか、広い範囲を見るか）
- triggered／continual（CI や定時など契機で動くか、常時評価するか）
- static／dynamic（固定しきい値か、他の値に連動する範囲か）
- quality attribute（品質特性。ISO/IEC 25010 などで分類）
- testing pyramid（テストの種類ごとの量の釣り合いを示すモデル）
- chaos engineering（本番に故障を注入して回復力を確かめる手法）

### 解釈・実務への示唆

- 「指標としきい値、いつ・どこで実行するか、外れたらどうするか」を1行で書く形は、品質目標をレビューできる形にする最小の型として使える。
- 作る順番は下層（CI で回る静的チェック）から。上層（本番の業務指標の監視）は効果が大きいが、数を絞る。
- 分類表の列（広さ・契機・場所・型・自動化・品質特性）を、今あるテストや監視の棚卸しに使うと、手薄な層が見える。

## 第3章 進化的アーキテクチャ

原題: *Evolutionary Architecture: Guiding Architecture with Testability and Deployability*／著者: Dave Farley

### 章の問い

将来の需要が読めない中で、過剰な先回り設計をせずに変更の余地を残すには何を指針にすればよいか。著者の答えは testability と deployability を軸に作業を組み立てること。

### 本の記述

- アーキテクチャは重要だが、その品質の判断は曖昧で主観的になりがち。アーキテクチャ文書は細部を決めすぎない観光地図のように使うのがよい［第3章 p.43］
- 複雑なシステムは段階的な学習の産物であり、使われ方や進化を事前に見通せると考えるのをやめるべき。開発者・利用者・組織を含む complex adaptive system の一部として、学びながら適応する必要がある［第3章 p.44］
- 答えを全部持たずに始め、学びが深まっても変更できる能力を守る、つまり選択肢を開いておくことが目標［第3章 p.44］
- 持続的な変更を支える5つの性質：modularity（他を巻き込まずに変えられる部品分割）、cohesion（一緒に変わるものを近くに置く）、separation of concerns（各部分が一つの問題に集中）、abstraction／information hiding（中を知らずに振る舞いを使える継ぎ目）、coupling（部分同士が一緒に変わる必要の度合い）［第3章 p.44］
- これらは技術に依存しない一般的な性質で、これを満たすシステムは扱いやすく、変えやすく、理解しやすく、テストしやすい［第3章 pp.44–45］
- 例：ドメインロジックと永続化を早い段階で分けていれば、RDBMS からグラフ DB へリポジトリを差し替えるのが比較的容易。混ざっていれば検討すら難しい［第3章 p.45］
- 品質は通常、作り手の技能・経験・意欲に左右される。加えて、動くことを確かめ、安全に変更する自由のためにテストが要る。手動テストは遅く高く信頼性が低いので、自動テストを選ぶ［第3章 p.45］
- テストしやすいコードの条件（状態を制御できる、振る舞いに集中できる、テストが実装詳細から切り離せる）は、上の5つの性質と一致する。だからテストに設計を導かせると、個人の技能だけに頼るより設計品質が上がる［第3章 pp.45–46］
- deployability はより大きなスケールで効く道具。continuous delivery では deployment pipeline がリリース可能性を決定的に判定し、その範囲は「commit からリリース可能な成果物まで」。通過後に他と組み合わせた追加テストが要るなら、そのパイプラインはリリース可能性を判定できていない［第3章 p.47］
- 評価を信頼できるものにするには、本番に出るコードそのものを、できるだけ決定的な振る舞いで評価する。よって deployment pipeline の正しい範囲は、独立してデプロイできる単位（マイクロサービス1つでも企業システム全体でもよい）［第3章 p.47］
- スケーラビリティや回復力に注力しても利用者が3人しかいなければ無駄になる。将来の需要を見越した過剰設計を避け、目の前の需要に合わせて早く始めて適応する方がよい［第3章 pp.47–48］
- testability と deployability を軸にすると、essential complexity と accidental complexity の分離が進み、セキュリティや回復力など他の特性を後から強化しやすくなる（例：必要になってから chaos testing を導入する）［第3章 p.48］

### 用語

- evolutionary architecture（学びに合わせて段階的に変えていく前提のアーキテクチャ）
- modularity／cohesion／coupling（部品分割、まとまりの強さ、部品同士の依存の強さ）
- separation of concerns（関心ごとに部分を分けること）
- abstraction／information hiding（実装詳細を隠して境界を作ること）
- testability（テストのしやすさ）
- deployability（独立してデプロイできる度合い）
- continuous delivery（ソフトウェアを常にリリース可能な状態に保つ実践）
- deployment pipeline（commit からリリース可能な成果物までの評価を自動化する仕組み）
- essential／accidental complexity（問題そのものの複雑さと、作り方に由来する複雑さ）

### 解釈・実務への示唆

- 設計の良さを直接測る代わりに、テストのしやすさとデプロイのしやすさを目安にできる。テストが書きにくいと感じたら、結合や関心の分け方を見直す合図として扱う。
- 「独立してデプロイできる単位を1本のパイプラインにする」という基準は、リポジトリやサービスの分け方を決めるときの判断材料になる。
- 将来の需要を見越した作り込みを避け、目の前の需要で始めて直していく姿勢は、個人開発でまず完成させる方針と合う。

## 第4章 Modularity Maturity Index でアーキテクチャを改善する

原題: *Improve Your Architecture with the Modularity Maturity Index*／著者: Dr. Carola Lilienthal

### 章の問い

レガシーシステムのアーキテクチャに溜まった technical debt の量をどう測り、リファクタリングか置き換えかをどう判断するか。

### 本の記述

- 過去20年、機能の早期実装を優先した結果、technical debt（保守費を押し上げる不要な複雑さ）が溜まり、保守や拡張が高価で不安定なレガシーシステムが増えた。MMI はどれをリファクタリングし、どれを置き換え、どれは放置してよいかの指針になる［第4章 p.49］
- technical debt を2種類に分ける：implementation debt（長いメソッドや空の catch などの code smell。ツールでほぼ自動検出でき、日常業務で返済する）と、design and architecture debt（クラス・パッケージ・層・モジュール間の依存が計画と合わない。数えるだけでは分からず、アーキテクチャレビューが要る）。ドキュメント不足やテスト不足、使いにくさは technical debt に含めない［第4章 p.50］
- 拡張のたびに debt は必ず生じるので、改善を定期的に挟めば「低く安定した保守コストの帯」に留まれる。改善が許されないと architecture erosion が進み、単位時間あたりに実装できる機能が減っていく。抜け出す道は refactoring か replacing［第4章 pp.50–51］
- MMI は著者の博士論文（建築と認知科学）と300件超のアーキテクチャ評価から作られた統一評価方式。人間の複雑さへの対処法（chunking、階層化、schema 形成）を、modularity・hierarchy・pattern consistency の3原則に対応させる［第4章 p.52］
- modularity：Parnas の「1モジュールに1つの設計判断」に基づく。評価の手がかりは、凝集と結合（結合は測れる）、名前（責務が一つか。測れない）、大きさの釣り合い（測れる）［第4章 p.53］
- 釣り合いの悪い例：9つのビルド単位のうち1つが約95万行で、残り8つは合計約8.5万行。巨大な「Monolith」が小さな衛星群を使う形になっていた［第4章 pp.53–54］
- hierarchy：包含関係（クラス→パッケージ→プロジェクト）は自然に階層を作るが、使用・継承関係は循環を作りうる。例：479クラス中242クラスが18ディレクトリにまたがる1つの循環を形成し、分解には大きな再設計が必要。別の例では8万行のシステムの4層（App、Services、Entities、Util）に逆向き参照があったが、原因は16クラスだけで容易に解消できた。循環はどのレベルでも測りやすい［第4章 pp.54–56］
- pattern consistency：schema（典型的な性質をまとめた抽象）があると理解が速い。デザインパターンが存在し、ソースから見つけられ、一貫して使われていることが重要。パターンを層として並べ、上から下への参照が多く逆向きが少なければ良好。直接は測れないので複数の指標で評価する［第4章 pp.56–57］
- MMI の重み：modularity 45%（ドメイン／技術のモジュール化 25%、内部インターフェース 10%、大きさの釣り合い 10%）、hierarchy 30%（層構造 15%、クラス・パッケージの循環 15%）、pattern consistency 25%。modularity が他2つの土台なので最も重い［第4章 pp.57–59］
- 各基準の判定方法は3種類：metrics tools（正確な値。ただしツールごとに実装が違う点に注意）、architecture analysis tools（測れるがレビュアーの洞察に依存）、reviewers（裁量による判断）。比較可能性のため、レビューは2人1組で行い、さらに大きなグループで結果を議論する［第4章 p.58］
- 基準の例：ドメインモジュールに割り当てられたコードの割合、層違反の割合、大きなクラス・メソッドにあるコードの割合、循環的複雑度の高いメソッドの割合、循環に含まれるクラス・パッケージの割合、1循環あたりのクラス数、パターンの明示（クラス名・継承・アノテーション）、ドメインと技術コードの分離（DDD、Quasar、Hexagonal）など［第4章 pp.58–59］
- 計算方法：各基準を表に沿って0〜10点に換算し、区分ごとに平均して原則の重みを掛け、全体で0〜10の値にする。換算表のしきい値の例：技術層の違反は 0.1% 未満で10点、6.5% 以上で0点。循環に含まれるクラスは 2.5% 未満で10点、25% 以上で0点。1循環あたりのクラス数は10未満で10点、106以上で0点［第4章 p.60］
- 判断基準：8〜10は debt が少なく低く安定した保守コストの帯。4〜8は debt がかなりあり、リファクタリングが必要（通常は置き換えより改修が安い）。4未満は保守・拡張に多大な労力がかかり、置き換えを検討する。図では5年間に評価した18システムを示す［第4章 pp.60–61, 63］
- アーキテクチャレビューの流れ：(1) 解析ツールでソースを読み込み実アーキテクチャを把握、(2) 目標アーキテクチャをその上にモデル化して比較、(3) 合わせるための簡単なリファクタリングを探す（実装の方が良いと分かることや、新しい目標像を作ることもある）、(4) debt とリファクタリング案を集める、(5) 大きなクラス、強すぎる結合、循環などのメトリクスを見てさらに debt を探す。使用ツールとして Lattix、Sotograph/SotoArc、Sonargraph、Structure101、TeamScale を挙げる［第4章 pp.61–63］
- 目標と実際がずれる理由：IDE は局所しか見せない、チームがアーキテクチャを知らない、時間に追われて意図的にずらし、リファクタリングが無期限に先送りされる［第4章 p.61］

### 用語

- technical debt（誤った・最適でない技術判断が後の作業を増やすこと。Ward Cunningham, 1992）
- implementation debt（code smell など、ソースから自動検出できる負債）
- design and architecture debt（モジュール間の依存が計画と合わない負債）
- architecture erosion（改善がされず、計画したアーキテクチャから実装が崩れていくこと）
- Modularity Maturity Index（MMI。modularity・hierarchy・pattern consistency から算出する0〜10の評価値）
- modularity／hierarchy／pattern consistency（MMI の3原則）
- cyclomatic complexity（分岐の多さから見るコードの複雑さ）
- class cycle／package cycle（クラスやパッケージ間の循環依存）
- target architecture／actual architecture（計画上の構造とソース上の実際の構造）
- schema（似たものの典型的性質をまとめた認知上の抽象）

### 解釈・実務への示唆

- 負債を「ツールで見つかる実装の負債」と「レビューでしか見つからない設計の負債」に分けると、CI に任せる点検と人が見る点検を分けられる。
- MMI の点数を出すより、基準の項目（層違反、循環、大きすぎるクラス、ドメインと技術コードの分離）を自分のコードの点検項目として借りる方が手軽。換算表のしきい値が他の言語や規模でも妥当かは未確認。
- 目標の構造を実際の依存関係に重ねて比べる手順は、小さなリポジトリでも依存グラフを描くツールで試せる。

## 第5章 プライベートビルドと指標

原題: *Private Builds and Metrics: Tools for Surviving DevOps Transitions*／著者: Christian Ciceri

### 章の問い

DevOps が理想どおりに根付いておらず、自動化が開発チームの手を離れている組織で、開発チームはどうやって trunk（共有の本線）を安定させ、品質と速度を保てばよいか。その状況をどの指標で捉えるか。

### 本の記述

- 対象とする「アンチパターン」は4つ。DevOps チームと QA チームの断絶、生産性のないフィードバックループ、理解を伴わない自動化への過度な依存、検証と自動化に対する当事者意識の喪失。［第5章 pp.65–66］
- 前提として、痛みを伴う作業ほど頻繁に行い自動化の候補にする（Fowler）、CI は少なくとも1日1回の統合を自動ビルドとテストで検証する実践、CD は ops や QA まで含めて自動化でつなぐもの、と整理する。欠陥は見つかるのが遅いほど修正コストが高く、最悪は本番でエンドユーザーが見つけるケース。［第5章 pp.66–67］
- DevOps の柱を Process（ops を開発チームに統合し、常にデリバリー可能な状態を保つ）、Tools（その状態に責任を持つチームがツールを選ぶ）、Culture（ops もコードと同じくバージョン管理する、互いの領域を越えて学ぶ）に分け、最も大きいのは文化の変化だとする。［第5章 pp.67–68］
- 著者が「ownership shift（当事者意識の移転）」と呼ぶアンチパターン：DevOps が「モダンな SysAdmin」職や、独自のチケットフローを持つ自動化専任チームの名前になり、開発チームはデプロイの場所も方法も知らないまま検証だけを任される。QA も別組織で、サイロと環境の不一致が戻ってくる。［第5章 p.68］
- Fowler の「壊れたビルドはすぐ直す」は、ビルドを壊すのはコード変更だけで、メンバーが自力でデバッグする権限と知識を持つ、という前提に立つ。ownership shift の下ではこの前提が崩れ、原因がコード外にあると DevOps チームへのチケット待ちになり、QA も最新版を確認できずデリバリーが止まる。誤りは CI/CD パイプラインを検証の中心に置くことだとする。［第5章 p.69］
- 提案は、検証の重心を問題が入り込む場所＝ローカル開発環境に戻すこと。手段は Duvall らの private build（共有の本線へ入れる前に、最新の他者の変更を取り込んだ統合ビルドを自分の環境で再現する）。目的は trunk や後段の検証に問題を入れないこと。完全自動化が難しい理由（テストデータの選定、DB マイグレーションの扱い、マイクロサービス間のメッセージブローカー、E2E テストのローカル実行の難しさ）を挙げ、自動化できない手順は一時的に手動でもよいとする。［第5章 pp.70–71］
- 事例1「不安定な trunk」（Company A）：QA が受け取る最新版がいつも壊れている。バグ4件を表にして分析（A1 フロントエンド：サーバーからの未定義値、A2 バックエンド：API に合わない型、A3 実データの形式が想定外、A4 後方互換性）。当初は A2 以外「避けられない」と見ていた。［第5章 p.72］
- 対策として、フロントエンド・DBA・DevOps のメンバーにもバックエンド環境をローカルで動かす方法を教え、バックエンドは API 契約テストの代わりに共有の手動テストケースで private build を回し、DBA はデータ変更のたびに pull 前後で手動テストを走らせた。QA は機能確認と E2E 自動化に時間を回せるようになった。再分析では4件とも「private build で回避可能」に変わった（自動化の容易さは A1 進行中、A2・A3 可、A4 不可）。［第5章 pp.72–74］
- 事例2「足止めされたコンサルタント」（Company B）：社内 DevOps チームが構築中のパイプラインが不安定で（テストデータの変更、マイグレーション停止、コンテナの再起動ループ、依存先のクラウド移行による停止）、専用テスト環境の用意に2週間かかる。チームは API テストを手元で更新の前後に手動実行し、頼れない外部サービスは偽のレプリカを作った。3回目のイテレーションで社内自動化から独立して検証でき、速度と修正の効果が上がった。［第5章 pp.74–75］
- 指標1 Time to Feedback（定性・間接、コストと time to market を測る）：新機能のフィードバックを得るまでの時間と労力。遅い自動化が原因のこともあれば、正式なフィードバックをくれる人が見つからないこともある。開発チームは自分の作業を止めるフィードバック（統合・QA）を優先する。間接指標なので問題の存在は示すが原因は示さない。［第5章 p.76］
- 指標2 Evitable Integration Issues in the Deployed Application per Iteration（定量・間接、社内の品質管理プロセスを測る）：デプロイ済みのソフトで見つかった統合不具合のうち、private build で簡単に見つけられたはずのものの件数。「QA で見つかったバグ数」との違いは「事前検証で容易に避けられたか」で分類する点。private build の範囲は、API 契約テストと、ログインのような全体に重要な機能や変更箇所の happy path テストを目安とする。［第5章 pp.76–77］
- 指標3 Time Spent Restoring Trunk Stability per Iteration（定量・直接、コードベースの安定性とそれを保つチームの力を測る）：更新（git pull）後の private build で見つかった、trunk に入り込んだ不具合のデバッグ・修正にかけた時間。機能を生まない作業の時間＝コストを直接測る。値が悪ければ private build の規律不足、ローカル環境の非標準化、テスト自動化の不足を疑う。［第5章 p.77］
- private build のコストへの反論（生産性とチェックイン頻度が落ちる）には、trunk の継続的な立て直し・QA との往復・チケット管理のほうが高くつくと答える。手動の統合検証は一時的なものとし、簡素なスモークテストにとどめ、繰り返す作業はすぐ自動化する。［第5章 p.78］
- 指標の組み合わせ別の読み方：Time to Feedback 高＋回避可能な不具合 多 が最も多いパターンで、検証が自動化と QA に寄りすぎ、ローカルで捕まえずに trunk に入れていると推測する（振り返りで回避可能性を分析、全員がローカルでフルテストを回せるようにする、最小の機能テストを共有、規律、繰り返し）。Time to Feedback 低＋不具合 多 は、定性指標の偏りか、QA が非効率を吸収している可能性。Time to Feedback 高＋不具合 少 は、QA プロセス全体の遅さか、trunk は健全だが官僚主義や DevOps の予定が遅延の原因かのどちらかで、後者ならチーム間の壁を取り除く。不具合 少＋trunk 復旧時間 長 は、メンバー間で private build の規律に偏りがあるサインで、振り返りで扱う。［第5章 pp.78–79］
  - 補足：本文の見出しでは trunk 安定化の指標が「Low Time to Trunk Stability」のように書かれ、指標3の定義（復旧にかかる時間）と高低の向きが一致しない箇所がある。向きの解釈は未確認。
- 結論：アーキテクチャの特性を測る前に、いつも壊れている trunk を安定させるべきで、そうしないと誤った結論を導く。private build は ownership shift の下で特に重要になり、ローカル環境に検証を戻すことでデリバリーの責任を開発チームに戻す。［第5章 p.80］

### 用語

- CI/CD（continuous integration / continuous delivery。本章の CD は continuous delivery の意味）
- DevOps（開発と運用の協働。本章では文化の変化を中心に置く）
- ownership shift（著者の造語。自動化と検証の当事者意識が開発チームから別チームへ移ってしまうアンチパターン）
- trunk / mainline（共有の本線ブランチ）
- trunk stability（本線が正しく動く状態にあること）
- private build（共有の本線へ入れる前に、自分の環境で統合ビルドと検証を行うこと。Duvall ら）
- smoke testing（主要機能が動くかだけを確かめる簡素なテスト）
- API contract test（API の入出力の約束が守られているかを確かめるテスト）
- 定性／定量、直接／間接指標（qualitative/quantitative、direct/indirect。間接指標は問題の存在を示すが原因は示さない）

### 解釈・実務への示唆

- 振り返りで「どの段階なら見つけられたか（手元／CI／ステージング／本番）」の列を足すと、どこの検証を厚くするかが決まる。
- 間接指標は問題の存在を示すが、原因は示さない。原因は指標を組み合わせて推測し、振り返りで確かめる。
- push 前に手元で回す最小セット（API 契約テストと、重要機能の happy path）を決めておくと、CI やレビュー待ちで止まる時間が減る。

## 第6章 組織のスケール

原題: *Scaling an Organization: The Central Role of Software Architecture*／著者: João Rosa

### 章の問い

成長期の組織で、アーキテクチャを場当たりではなく意図をもって進化させるには、組織の使命や KPI とアーキテクチャ上の指標をどうつなげればよいか。

### 本の記述

- 章は架空の人物 Anna（複数人の合成）とフィンテックのスケールアップ企業 YourFinFreedom の物語で進む。PSD2 を活用してベネルクスから EU の大国へ展開しようとしており、成功の結果として可用性の問題が起きている。著者は設計図ではなく、指標を抽出してアーキテクチャの判断につなげる進め方を示すとする。［第6章 pp.81–82］
- アーキテクチャは組織構造と、その中のコミュニケーションの2つを映す。後者は暗黙的で、意図して設計しないとアーキテクチャはチームの組織と会話の形をなぞる（Conway's Law）。［第6章 pp.82–83］
- 部門長 Keisha はモノリスをマイクロサービスへ分割し、チームを3から10に増やす決定をした。どちらの様式も正しく実装すれば健全だが、モノリスは big ball of mud に、マイクロサービスは distributed big ball of mud（ネットワーク越しに分散して複雑さが増したもの）に流れやすい。人を増やして既存の中央集権的な構造に手を加えると accidental complexity（依存、文書化・テストされていないコード、構造のない設計）が増え、保守性・運用性・変更容易性が落ちる。過剰設計されたマイクロサービスでは、1つの業務トランザクションを理解するための cognitive load が人の容量を超える。［第6章 pp.83–85］
- 1年後の症状：機能を出すためのマイクロサービス間のリリース調整（release orchestration）、サービス間の機能の重複で責任が持てない、優先度が頻繁に変わり作業が捨てられる、品質問題による士気低下、製品の方向性がわからない。Anna は指標と明確な境界の導入を提案し、Solutions Architect に昇格する（条件は社内のあらゆる部門と話す許可）。［第6章 pp.85–86］
- 会社の KPI：財務の EBITDA と customer lifetime value に加え、使命に合わせて MAU（月間アクティブユーザー）を導入。アーキテクチャは組織の使命と KPI につながっている必要があり、KPI が曖昧または理解されていないとアーキテクチャは KPI と食い違う。アーキテクチャの役割は、構成要素の責任の境界と相互作用を定め、技術・人・規制・市場などの制約を尊重しつつ事業の機敏さを可能にすること。［第6章 pp.87–88］
- 「best effort」から「intentional effort」へ：全員がすべての依頼に精一杯応える状態では、判断に意図がない。Anna は Big Picture EventStorming を開き、業務イベントの流れと順序を可視化し、仕事の種類が変わる所や処理が終わる所に境界を引いて、浮かび上がるドメインを見つけた。その上に現行のソフトウェア部品とその所有チームを重ねると、プロセスと実装の不一致、1チームが散らばった部品を持つことによる高い cognitive load が見えた。最後に各ドメインの KPI も書き込んだ。［第6章 pp.88–90］
- 著者の実例：税務当局と港をつなぐソフトの会社で EventStorming を行ったところ、サポート担当が船舶取引の文脈で税務書類を修正している運用が現地法に抵触すると税務弁護士が指摘し、ソフトを修正できた。改善を検証する KPI もそこで議論し、バックログの優先順位付けに使えた。［第6章 pp.90–91］
- 次に Process Modeling EventStorming で、Travel Insurance ドメインの1つの operational value stream「旅行保険の見積もり依頼」を掘り下げた。KPI を書き込むと人によって定義が違うことがわかり、定義をそろえる機会になった。hotspot（日々の作業の困りごと）も書き出す。「会社はどこで稼ぐのか」を問い、ビジネスモデル（有効化された保険契約ごとの手数料）を理解する。著者の経験則は「slower is faster」（KPI の理解に時間をかけるほど後で速くなる）。［第6章 pp.91–92］
- hotspot の分析は無駄の発見につながる。Lean（トヨタ生産方式）の8種類の無駄を、アーキテクチャ上のトレードオフを検討するときの視点の1つとして使い、境界をどこに置くかの指針にすることを勧める（Lean の詳細は章の範囲外）。［第6章 pp.92–93］
- ドメイン分解（outcome → goals → metrics）：指標はアーキテクチャに近く頻繁に変わり、目標はゆっくり変わって方向を示す。指標は fitness function として実装することもできる。［第6章 pp.93–94］
- 計画：「micro」ではなくなっていた中央の顧客情報サービスと旅行保険サービスが絡み合い、リリース調整を生んでいた。3つの問い（旅行保険契約を自己完結したサービスで管理できるか、依存の移動にかかる労力、データの移動にかかる労力）を実験で確かめる。新サービスは当初プロキシとして両方に書き込み、信頼性を証明する。仮説は「旅行保険のロジックを移すと、顧客情報サービスの deployment frequency が上がり change fail rate が下がる」。［第6章 pp.94–95］
- KPI Value Tree：3階層で、1段目は組織 KPI（EBITDA、customer lifetime value、MAU など。結果を振り返る lagging indicator）、2段目はドメイン KPI（有効化された契約の割合を上げる、見積もり依頼から有効化またはキャンセルまでの時間を縮める。これも lagging）、3段目は指標（見積もりのマッチングにかかる時間、手作業のデータ修正の件数、顧客入力のデータ品質が lagging、deployment frequency と change fail rate が leading indicator）。ツリーはある時点のスナップショットで、継続的に見直す。［第6章 pp.95–97］
- Goodhart's Law：KPI や指標は目標（target）ではなく道しるべとして使う。「KPI X を達成できていない」という言い方が出たら目標化しているサイン。目標が必要なら KPI や指標と呼ばず目標と呼ぶ。SLA を負うサービスなら目標を持つのは妥当で、KPI・指標・目標のつながりを可視化するとよい。［第6章 p.97］
- 著者がよく使う指標：DORA の4指標（lead time、deployment frequency、change fail rate、mean time to restore。速度と安定性の leading indicator）、可観測性が整っていれば mean time to discover（障害発生から発見までの平均時間）、throughput（チームが仕事のまとまりを届ける力の基準値）、employee Net Promoter Score。すべてを機械的に使うのではなく、これらでチーム間を比較するのは逆効果とする。［第6章 pp.97–98］
- 著者の実例：銀行のモバイルアプリ部門で、DORA 指標にしきい値を設けて全社のチームを格付けしようという声があったが、メインフレームからサーバーレスまで文脈が違うため反対した。モバイルアプリでは頻繁なデプロイが更新通知を増やし顧客の NPS を下げるため、alpha・beta・production の3つの deployment ring を設け、すべての変更を alpha に自動デプロイする形でいつでもデプロイできる能力を持たせた。［第6章 pp.98–99］
- 期待値の管理：実験中は機能開発の能力が下がることを、予見できる影響・狙う成果・会社目標への貢献と合わせて関係者に明示する。実験は成功し、境界を引き直した Travel Insurance ではリリース調整が不要になった。のちに「見積もりマッチング時間の短縮」は、市場拡大に比例してアナリストを増やす必要がありEBITDA を圧迫すると予測され、「アナリストが提示した選択肢から最初に受け入れられた見積もりの割合を上げる」に置き換えた。入力を処理して保険会社に問い合わせ、選択肢を作る意思決定支援サービスを導入した。［第6章 pp.99–101］
- 著者の実例（EC の在庫補充ドメイン）：最適な仕入先を計算する API の失敗率が高く、失敗を補充対象の商品と関連づける指標を作ったところ、供給終了なのにシステム上は廃番になっていない商品が原因だと判明。指標に反映すると API エラーはほぼゼロになり、エンドツーエンドの処理時間も大きく改善した。［第6章 pp.101–102］
- 他ドメインで見えた3つのパターン：アーキテクチャがドメイン境界と合っていない、ドメイン境界そのものが誤っている（全金融ドメインの情報を持つ中央の顧客情報サービス）、ドメインやバリューストリームをまたぐ部品を持つチームの cognitive load が高い（無関係な Customer Onboarding と Billing を同じチームが担当）。対策として顧客情報サービスを Identity Management と Account Management などに分け、所有の見直しも行う。［第6章 pp.102–103］
- 指標の値よりトレンドが重要なことがある。mean time to discover の悪化は、アーキテクチャの複雑化と cognitive load の増加による従業員エンゲージメント低下を示しうる。mean time to discover と change fail rate を組み合わせると弱点の発見に、change fail rate と employee NPS を組み合わせると管理者による支援に使える。他社の指標をそのまま写しても文脈が違うので機能しない。［第6章 pp.103–104］

### 用語

- Conway's Law（システムの設計は、それを作る組織のコミュニケーション構造を写すという法則）
- big ball of mud / distributed big ball of mud（構造のないスパゲッティ状のシステム／それがネットワーク越しに分散したもの）
- accidental complexity（問題そのものではなく、作り方によって持ち込まれた複雑さ）
- cognitive load（一度に頭に保持できる情報量の限界。チームでは全員の容量の合計。Team Topologies）
- release orchestration（1つの機能を出すために複数サービスのリリースを調整すること）
- EventStorming（Big Picture / Process Modeling）（業務イベントを付箋で並べ、境界や課題を共同で可視化するワークショップ手法）
- operational value stream（顧客に価値を届ける一連の業務の流れ）
- hotspot（EventStorming で書き出す困りごとや論点）
- KPI Value Tree（組織 KPI → ドメイン KPI → 指標を3階層でつなぐ図）

- fitness function（アーキテクチャ特性を客観的に評価する仕組み）

### 解釈・実務への示唆

- 技術指標は単独で選ばず、組織や製品の目的（KPI）から木の形でつなげて選ぶ。つながりを説明できない指標は優先度を下げる。
- 指標を目標にすると歪む（Goodhart's Law）。目標が要るものは「目標」と呼び分ける。たとえば SLO は目標、DORA の4指標は道しるべとして扱う。
- DORA の4指標でチーム同士を比べない。比べるなら同じチームの推移を見る。

## 第7章 ソフトウェアアーキテクチャにおける測定の役割

原題: *The Role of Measurement in Software Architecture*／著者: Eoin Woods

### 章の問い

アーキテクチャ作業を前倒しの設計ではなくデリバリー全体に分散させるとき、十分な作業をしたか、最も重要なことに時間を使っているかをどう判断するか。著者の答えは「品質特性を継続的に測る」こと。

### 本の記述

- アーキテクチャ上の重要な判断の多くは、性能・回復力・セキュリティなどの quality attribute（非機能品質）に関わり、品質間のトレードオフを伴う（回復力を優先すると性能が落ちる、など）。昔は前倒しの設計で対処したが、いまは continuous delivery、RCDA、continuous architecture のようにライフサイクル全体でアーキテクチャ作業を行い、判断を情報が増えた後へ遅らせる。そこで問題になるのが「どこまでやれば十分か」で、測定がその答えだとする。一時点の測定で現在地が、時系列の測定でトレンドと行き先がわかる。［第7章 pp.105–106］
- 従来は定義・設計・構築の後に測定を始めることが多く、反復的なチームでも本番後まで測定を後回しにしがち。define-design-build-deploy を継続的に回し、早くから継続的に測る。測定が注意の優先順位を決め、アーキテクチャ判断を生み、変更の効果をまた測るサイクルにする。［第7章 pp.106–107］
- 測定の4分類（artifact / operational × external / internal）：［第7章 pp.107–108］
  - external artifact：設計文書による標準・ガイドライン（例：GDPR）への準拠の評価。判断に頼るため最も弱いが、設計の最初期に行え、関係者の信頼を得るのに役立つ。
  - internal artifact：コードの複雑度、モジュールの結合度、DB スキーマ要素数など。正確で安価、保守性・拡張性の指標になるが、成果物（多くはコード）ができるまで測れない。
  - external operational：応答時間、throughput、障害からの復旧時間、月あたり障害数など。本番稼働が必要だが、ユーザーが体験するものを捉える。
  - internal operational：メモリ使用量、データ量の伸びに対する DB インデックスの伸び率など。将来の問題の予測に役立つ。
- 実行時の測定手段は logs・traces・metrics の3つ（Cindy Sridharan の整理を紹介）。インフラ側はクラウドの収集基盤で容易に取れるが、アプリ側は自前実装や APM が必要。その分、売上のような関係者が本当に気にする文脈固有の情報を得られる。［第7章 pp.108–109］
- 静的コード解析は、よくある誤りと構造（複雑度・結合度）を測れるが、保守性・拡張性以外の品質はあまり評価できない。セキュリティについては検出された脆弱性数が代理指標になる。コード解析は事後的なので、実装前に最小限で正確な設計表現を残して design analysis を行えば、標準準拠やスケーラビリティを予測的に測れる（詳細な設計書は勧めない）。［第7章 p.109］
- estimates and models：過去の経験、類似システムの測定値、公開ベンチマークから、運用パラメータ（DB サイズ、リクエスト量と種類、サーバー台数、メモリ）と品質値の関係を表計算でモデル化する。数値化しやすい性能・スケーラビリティ向きでセキュリティには使いにくい。理解できる単純さで信頼できる結果を出すのは難しく、予測力の検証は実物ができるまで難しい。［第7章 pp.109–110］
- fitness function は新しい測定手段ではなく、測定値を使って品質が許容範囲内にあるかを監視する仕組み。自動化が理想だが、表計算のような手動のものでも価値がある。例：ある種類のリクエストは 100 ms 以内という要件なら、本番で応答時間を監視し遅くなったら警告する。［第7章 p.110］
- 性能：決まった仕事をどれだけ速く処理するか。latency（1件の処理時間）と throughput（一定時間に処理できる件数）で測り、両者は反比例するはずとする。スケーラビリティとは別物だが、性能劣化はスケーラビリティ問題の症状であることが多い。決め手は仕事量と処理の効率（インデックスの有無など）。応答時間は1回の測定では意味が薄く、分布を平均・中央値・ばらつきで特徴づけ、要件との差の大きさでアーキテクチャ上の対応が必要か判断する。より良い資源を「買う」ことで改善できるがコストとのトレードオフがある。［第7章 pp.111–112］
- 性能測定の落とし穴：テスト環境と本番の差（データ、負荷パターン、構成）、モデルと現実の差（早くテストして較正する）、再現性のある現実的な負荷の生成の難しさ、分散システムの間欠的な現象（無視せず調べる機会にする）、性能測定用のログ不足、逆にログ過多（明確なログ戦略と設定可能なログ機構で防ぐ）。［第7章 p.112］
- スケーラビリティ：負荷の増加にどう応えるか、つまり使える資源に対して処理能力がどう変わるか。理想は線形（資源 50% 増で処理 50% 増）だが実際にはまれ。リクエスト処理能力、バッチ throughput、データ保存容量、組織（人とプロセス）の容量という複数の観点がある。測り方の例：ある構成で、平均応答時間 0.5 秒・95% が 2 秒未満という条件で 5 秒間に処理できるリクエスト数を測り、資源を 20% ずつ増やして比率を見る。資源コスト、保存容量とそのコスト、一定の負荷を支えるのに必要な人数（例外対応の業務スタッフ、定常作業の運用スタッフ）も測定対象になる。［第7章 pp.113–114］
- スケーラビリティ測定の落とし穴：予期しないボトルネック、予期しない非線形な振る舞い（どちらも探索的なテストで学ぶ）、複数種類の資源の組み合わせ（DB の拡張には CPU・メモリ・ディスク I/O が要る。CPU とメモリの関係を測る指標を作るなど）。［第7章 p.114］
- 可用性：指定期間のうちサービスが使えた割合。計画停止と障害の両方が影響する。MTBF（障害の頻度）と MTTR（復旧時間）があり、Allspaw が2010年に「復旧時間のほうが重要なことが多い」と指摘して MTTR が注目された。MTTR は設計・見積もり・テストができるが MTBF は障害が十分起きるまで推定しにくい。実際的には MTTR をモデル化・テストし、MTBF の粗い見積もりと組み合わせて可用性を推定し、実測で補正する。データ損失には RPO（失ってよいデータ量。「10分間の更新」「100トランザクション」など）と RTO（障害後にデータが使えるまで待てる時間）を使う。一部データだけでサービスを再開できる場合は RTO が MTTR より長くなる。RPO と RTO は通常反比例する。［第7章 pp.114–115］
- 可用性測定の落とし穴：MTBF は組織内の他システムの障害情報を代理に使うしかない、構成要素ごとに失敗の仕方が違うので MTTR・MTBF・RPO・RTO の組を全体へどう合成するか考える、「nines」の専制（99.99% は週約1分、99.999% は日約1秒の停止。障害の種類やタイミングを無視しており、100% に近すぎて意味が薄い）。nines で書かれた要件を警戒し、障害シナリオから業務上の必要を理解する。［第7章 pp.115–116］
- セキュリティ：重要だが測るのが非常に難しい。インシデント数を待たず、静的コード解析（潜在的脆弱性数）、動的解析（自動・手動のペネトレーションテスト）、インフラスキャンを代理指標として継続的に測り、発生可能性と影響でリスク重み付けして集計する。これはセキュリティそのものではなくテスト結果の測定だが、良くなっているか悪くなっているかを判断する最善の方法とする。落とし穴は、環境の構成差、テストと本番で別のセキュリティ ID を使うことによる差、誤検知（測定から除く）、リスク重み付けの難しさ（専門家に相談）、いつ止めるかの判断（体系的で一貫したデータに基づく専門家の判断）。［第7章 pp.116–118］
- 始め方の6原則：小さく始める（何でも集めるより行動につながるものから）、重要なものを測る（測りやすさではなく影響で選ぶ）、測った結果で行動する、早く始める、測定を見える化する（影響力のある人に定期的に報告）、測定を継続的にする（各部分を作るときにどう測るかを考える）。［第7章 pp.118–119］
- 架空の事例 Civis（人口12万人の自治体の住民向けプラットフォーム。コンテナ上の Java サービス、クラウドのマネージド RDB、API ゲートウェイ、Web と Android・iOS アプリ）：設計時に表計算で DB のテーブル数・行数・容量を見積もる（internal artifact）、パイプラインに静的解析の複雑度を入れ、しきい値超過でビルドを止める Python スクリプトを fitness function にする、静的セキュリティ解析から集計した脆弱性指標を毎回保存してトレンドを見る（不安定なうちは fitness function にしない）、CI で応答時間テストを回し許容範囲外で警告する fitness function を作る（external operational）、復旧時間テストと表計算モデルを手動の fitness function として可用性を見積もる。本番後は DB サイズとテーブルごとの件数を当初の見積もりと比べ、障害間隔と復旧時間を手で記録して実際の可用性を住民を含む関係者にほぼリアルタイムで報告する。測定は追加も削除もしながら続ける。［第7章 pp.119–121］
- 陥りやすい失敗：測定値ではなく測定の仕組みづくりに没頭する、測りやすさで測定を選ぶ、技術的な測定に偏り業務の測定（1時間あたりの売上など）を軽視する、測っても行動しない（スプリントの一定割合を測定結果への対応に充てる案）、有用性より精度を優先する、測りすぎる（定期的に見直し、不要な測定は止める）。［第7章 pp.121–122］
- 結論：品質特性の測定は、アーキテクチャ作業が効いているかを知る数少ない方法で、作業の優先順位付けを助け、品質要件を具体的にさせる（測れないことも明らかになる）。測定は4分類で整理して価値と限界を理解し、可能なら fitness function を通じて要件と比較するフィードバックループに組み込む。［第7章 p.123］

### 用語

- quality attribute / nonfunctional quality（性能・回復力・セキュリティなどのシステム品質）
- continuous architecture（アーキテクチャ作業を前倒しせずデリバリー全体で行う進め方）
- artifact / operational measurement（成果物からの測定／稼働中システムの測定）
- external / internal measurement（開発・運用チーム外に見える・影響する測定／チーム内に見える測定）
- logs / traces / metrics（時系列のイベント記録／コンポーネントをまたぐ関連イベントの集まり／数値の測定値）
- APM（application performance management。アプリの性能を測る製品）
- static code analysis / design analysis（コードの静的解析／実装前の設計表現の分析）
- fitness function（測定値で品質特性が許容範囲内かを確かめる仕組み。自動・手動の両方がある）
- latency / throughput（1件の処理時間／一定時間の処理件数）
- scalability（負荷の増加に対し、資源に応じて処理能力がどう伸びるか）
- MTBF / MTTR（平均故障間隔／平均復旧時間）
- RPO / RTO（失ってよいデータ量／データが使えるまで待てる時間）
- "the nines"（99.99% のような可用性の割合表記）
- penetration testing / dynamic analysis（稼働中のシステムに攻撃を試みて脆弱性を探すテスト）
- proxy measurement（直接測れない品質を間接的な値で代わりに測ること）

### 解釈・実務への示唆

- 4分類（artifact／operational × external／internal）は、測定の抜けを見つける枠として使える。ログ・トレース・メトリクスは、このうち operational な測定の手段にあたる（[ログ設計](../../logging/README.md)）。
- 可用性の要件は 99.9% のような nines から決めず、どんな障害がいつ起きたら業務が困るかのシナリオから決める。
- 測りやすいものではなく、結果を見て行動が変わるものから小さく始め、使わなくなった測定は止める。

## 第8章 メトリクスからエンジニアリングへ

原題: *Progressing from Metrics to Engineering*／著者: Neal Ford

### 章の問い

測っただけのメトリクスを、どうすれば設計を守る仕組み（エンジニアリング）に変えられるか。答えは、客観的なしきい値を持つ fitness function として自動で継続的に実行すること。

### 本の記述

- 物理学の数式が現実世界との対応づけを経て機械工学になったのと同様に、メトリクスも有用な文脈で評価されて初めてエンジニアリングの実践になる。アーキテクトは何十年もメトリクスを使ってきたが、場当たり的だった［第8章 p.125］
- architecture fitness function は *Building Evolutionary Architectures* で定義された概念で、「アーキテクチャ特性を客観的に評価する基準を与える、あらゆる仕組み」を指す。名前は遺伝的アルゴリズムで解の良さを判定する目的関数に由来する［第8章 pp.125–126］
- 定義の3語の解説: (1) architecture characteristics＝性能・スケーラビリティ・可用性など非ドメインの設計上の関心事。ドメインの検証には単体・機能・受け入れテストという成熟した道具があるが、特性の検証はビルド時チェック、本番モニタ、ログなどに散らばっていた。fitness function はそれらを一つの傘の下にまとめる。(2) objective evaluation criteria＝客観的に測れなければ検証できない。測り方が分からない特性（例: reliability）は composite（複合特性）であり、さらに分解すべき合図。(3) any mechanism＝テストライブラリ、性能モニタ、chaos engineering など複数の道具を使う［第8章 pp.126–127］
- fitness function は単体テストと重なりつつ、コードレベルのメトリクス、SonarQube などの評価ツール、運用モニタ、Netflix の Simian Army のような全体ストレステストまでを含む。ただし自動化して初めてエンジニアリングになる［第8章 p.127］
- メトリクスがダッシュボードに並ぶだけで、客観的なしきい値を設けて定期実行しなければ、それは事後の証拠にとどまり、予防の力にならない。コード変更のたびに自動実行するのが望ましい［第8章 p.127］
- 例: コンポーネント間の cyclic dependency は再利用時に絡んだ部品をすべて引き連れるため antipattern。IDE の自動 import を反射的に受け入れることで、ときどき循環が生まれる。ArchUnit（JUnit ベースのアーキテクチャテスト用ツール）でパッケージ範囲の循環なしをテストし、CI/CD パイプラインに単体・機能・受け入れテストと並べて組み込めば、違反をすぐに捕まえられる［第8章 pp.128–130］
- 自動化の歴史的教訓: XP の continuous integration（少なくとも1日1回メインラインにコミット）は、最後にまとめて統合するよりマージ作業の総時間を減らした。DevOps でも Puppet や Chef による構成自動化が一貫性をもたらした。同様に、コードレビューやアーキテクチャレビュー委員会といった手作業の統制を、CI に結びついた fitness function に置き換えられる［第8章 pp.130–131］
- 事例（結合度）: レイヤードアーキテクチャの層間アクセス規則（Controller はどこからも呼ばれない、Service は Controller からのみ、Persistence は Service からのみ）を ArchUnit のテストで表現できる。.NET には NetArchTest がある。ただしこれらは特定プラットフォームのコンパイル時検証に限られる［第8章 pp.132–134］
- 分散アーキテクチャでは既製ツールがないので自作する。例: オーケストレータ型マイクロサービスで「ドメインサービスはオーケストレータとしか通信しない」規則を、各サービスの直近24時間の呼び出しログを読み、宛先がオーケストレータ以外なら失敗にする擬似コードで検証する。ログでなくモニタを使うならイベントハンドラでリアルタイムに警告を出す形にもできる［第8章 pp.134–135］
- 事例（ゼロデイ脆弱性）: Equifax は 2017年3月7日に Apache Struts の脆弱性（CVE-2017-5638）とパッチが公表され、3月15日にスキャンも行ったが、一部の古いシステムへの適用が7月29日まで遅れ、9月に侵害を公表した。全プロジェクト（休眠中も含む）にデプロイパイプラインがあり、セキュリティチームが自分のステージに fitness function を差し込めれば、特定フレームワークの特定バージョンを検出してビルドを失敗させ通知できた［第8章 pp.136–137］
- パイプラインはコードだけでなく、DB スキーマ、デプロイ設定、fitness function 自体の変更でも起動するよう構成する。これでメトリクスの適用範囲を組織全体の統制にまで広げられる。また fitness function はコードなので、アーキテクトがシステムの変化を追い続ける動機にもなる［第8章 p.136］
- 事例（fidelity fitness function）: 新旧実装が同じ結果を出すことを保証する手段。GitHub はマージ処理をシェルスクリプト＋git コマンドからインメモリ実装へ置き換える際、Scientist を作った。use 節（旧コード）は常に実行して結果を返し、try 節（新コード）はリクエストの1%で実行。順序をランダム化し、結果を比較し、try の例外は握りつぶして記録し、ダッシュボードに出す［第8章 pp.138–139］
- GitHub は1日平均60回デプロイしており、この実験中も継続デプロイを続けながら新コードのバグを直した。4日間で1,000万回超の実験を行い、不一致も遅延もない24時間が得られた時点で旧コードを削除した。Scientist は feature toggle と性能メトリクスで実装した fidelity fitness function と位置づけられる［第8章 pp.140–141］
- 結論: fitness function を作り込みすぎて開発者を苛立たせてはいけない。目的は「重要だが緊急でない」原則の実行可能なチェックリスト。緊急の仕事に追われて後回しになることが技術的負債の典型的な原因で、ビルドで回るチェックリストなら飛ばせない。外科医やパイロットのチェックリスト（Gawande *The Checklist Manifesto*）と同じ発想［第8章 pp.141–142］

### 用語

- architecture fitness function（アーキテクチャ特性を客観的に評価する仕組みの総称）
- architecture characteristics（非機能要件・品質特性。ドメイン以外の設計上の関心事）
- composite architecture characteristic（reliability のように、複数の測定可能な特性から成る複合特性）
- cyclic dependency（コンポーネント同士の循環依存）
- ArchUnit / NetArchTest（Java / .NET でアーキテクチャ規則を単体テストとして書くライブラリ）
- deployment pipeline（コード変更などを契機にビルド・検証・デプロイを段階的に行う仕組み）
- fidelity fitness function（新旧実装の結果一致を検証する fitness function）
- Scientist（GitHub の実験用ライブラリ。use と try を並走させて比較する）
- feature toggle（機能の有効・無効を実行時に切り替える仕組み）

### 解釈・実務への示唆

- ダッシュボードに並べるだけの指標は事後の証拠にとどまる。しきい値を決めて変更のたびに自動で回したとき、設計を守る仕組みになる。
- 測り方が決まらない特性（reliability など）は、複数の特性が混ざった合図として、測れる単位まで分解する。
- 新旧実装を並走させて結果を比べる方法（Scientist）は、移行時に「一致・不一致・例外」を記録する設計の具体例として使える。

## 第9章 ソフトウェアメトリクスで保守性を守る

原題: *Using Software Metrics to Ensure Maintainability*／著者: Alexander von Zitzewitz

### 章の問い

構造の劣化（structural erosion）を早期に検知し、保守性を保つには、どのメトリクスをどんなしきい値で、どう運用すればよいか。

### 本の記述

- 最良の使い方は metrics-based feedback loop: 測定可能な目標を定め、実装しながら継続的に検証し、外れたら改善して戻す。レガシーでは最初から標準の目標を当てると違反が大量に出て士気を下げるので、緩い目標から始めて段階的に締める。ただし今も開発中で価値のあるシステムに限る［第9章 pp.143–144］
- 最大の敵は entropy（structural erosion）で、行き着く先が big ball of mud。症状は、無関係な箇所の変更で別の箇所が壊れることと、大きな cycle group（循環依存で結ばれた要素の集まり）［第9章 pp.144–145］
- 事例: Apache Cassandra の最大 cycle group は v2 で約450ファイル、v3 で900超、v4 で1,300超へ拡大し、v4 では新たに143と31要素の群も生じた。全要素の約75%が大きな cycle group に含まれる。パッケージ単位では113中102が一つの cycle group に入る。著者は一定規模を超えて成長し続ける cycle group を「code cancer」と呼ぶ［第9章 pp.145–146］
- 循環依存の害: 単独でテストできない、新人が理解しにくい、機能を切り出して差し替えられない（モジュール化できない）。循環は dependency inversion principle（インターフェースを挟んで依存の向きを反転）、上位クラスへの引き上げ、下位クラスへの押し下げ、機能の移動などで必ず断ち切れる［第9章 pp.146–147］
- 運用例: 最大の source file cycle group の要素数にしきい値5を置き、6以上で警告（またはビルド失敗）にする。小さいうちなら直すのは簡単。著者の経験では10万行超の非自明なシステムの8割超が big ball of mud になる。Spring は小さな cycle group しか持たない好例［第9章 pp.147–148］
- メトリクスが普及しない理由: 教育で扱われない、収集ツールがニッチ、文脈と専門性が要る（誤った指標を選ぶとメトリクスを満たすだけの表面的改善になる）、ルールが多すぎると逆効果（適量は5〜6個）、技術的負債で改善の余力がない、違反が行動につながる自動化が必要［第9章 pp.148–149］
- ツール: 自作は言語の進化への追随や依存モデル構築（コンパイラの構文解析と依存解決に相当）が必要で割に合わない。Understand、NDepend、Source Monitor、SonarQube は主にサイズと複雑度、Sonargraph-Explorer（Java・C#・Python は無料）は結合度・循環まで扱い、商用版は変更履歴と C/C++ にも対応。選定基準は自動ビルドでしきい値を検査できること（ツール対応状況は2022年初頭時点の記述）［第9章 pp.148–149］
- 結合度の指標: ACD（Average Component Dependency, Lakos）は各要素が直接・間接に依存する要素数（自身を含む）の平均。合計が CCD。PC（Propagation Cost）＝ACD/n＝CCD/n²で、変更が平均で全体の何%に波及しうるかを表す。図の例では CCD=18、ACD=3、PC=50%。Depends Upon と Used From、Fan In / Fan Out も基礎指標として使う［第9章 pp.150–152］
- PC の判断基準: 小規模（n<500）は高くても気にしにくい。中規模（500≦n<5,000）は20%超で懸念、50%超は大きな cycle group による深刻な問題。巨大（n≧5,000）は10%でも懸念（ACD=500 に相当）。部品数が増えると PC は自然に下がるので、下がった＝良いとは限らない。ACD も併せて見る［第9章 p.152］
- 循環の指標: 最大 cycle group のサイズはコンポーネントで5以下が目安。パッケージ・名前空間の循環はゼロ許容。Relative Cyclicity＝100×√(各 cycle group の要素数²の合計)/n。100要素が一つの群なら100%、2要素の群が50個なら約14.14%。小さい群ほど断ち切りやすい［第9章 pp.153–154］
- Structural Debt Index（SDI）: 同じ Relative Cyclicity 100% でも、10ファイルの一周循環なら1本切れば済み、全ファイル相互依存なら45本以上切る必要がある。SDI＝10×切るべきリンク数＋切るリンクの重み（使用箇所数）の合計で、解消作業量にほぼ比例させる。Relative Cyclicity と併用し、ゼロに近づける。増え続けるなら code cancer の兆候［第9章 pp.154–155］
- Maintainability Level（ML、著者による実験的指標）: 循環群を一つの論理ノードにまとめて依存グラフを階層化し、上位層への影響が少ないノードほど高く寄与させる。5要素超の cycle group にはペナルティ（5/サイズ）、100要素未満の小規模系には下限を上げる補正（例: 40要素なら60未満にならない）、パッケージ構造の乱れには Relative Cyclicity ベースの代替値を用いる。良い設計で90超、Cassandra は20台。Decoupling Level（DL）から着想を得たが DL は一部特許で再現不可［第9章 pp.155–160］
- サイズと複雑度の指標と推奨しきい値: ファイルは約800 LoC（ソフトしきい値）、関数・メソッドは Number of Statements 100、Cyclomatic Complexity（McCabe）は24超でエラー率が急増するため15、最大インデント深さ4。平均は Number of Statements で重み付けし、getter/setter による希釈を防ぐ。Modified 版は switch を1と数え、Extended 版は && と || も加算する［第9章 pp.160–162］
- 変更履歴の指標（Tornhill *Your Code as a Crime Scene* を参照）: Number of Changes(d)、Code Churn(d) と Churn Rate（例: 90日で2＝2回書き直し相当）、Number of Authors(d)（365日で1人なら知識の独占リスク）。複雑で頻繁に変わるファイル＝ホットスポットはリファクタリング候補で、依存の多い bottleneck class と重なりやすい。software city 可視化（底面積＝LoC、高さ＝平均複雑度、色＝90日の変更頻度）で一覧できる［第9章 pp.162–163］
- その他の指標: Component Rank は PageRank の応用で、新しいコードを読むときの起点（被参照の多いクラス）を示す。LCOM4 はメソッドとフィールドの連結成分数で、1より大きければクラスを分割できる（単一責任原則違反の検出）。ただしクラス階層では誤りやすい［第9章 pp.163–165］
- fitness function としての使い方: 特性はトレードオフになるので、優先するのは最大3つ＋保守性。保守性の目安として ML 75%以上、Relative Cyclicity はコンポーネント4%以下・パッケージ0%、SDI は100台前半。複雑なファイル（平均インデント3超、平均複雑度10超、800 LoC 超など）の LoC が全体の10%を超えないようにする、といった組み合わせも可能。CI で検査し、違反でビルドを止める［第9章 pp.165–166］
- 推移の追跡: 1日1回自動ビルドでメトリクスを集め、トレンドチャートにする。hard threshold はビルドを壊し、soft threshold は警告のみ。fitness function と結合度・サイズ指標を併せて追うと悪化傾向を早く掴める［第9章 p.167］
- 黄金律: (1) 部品と許可された依存を定義した、強制可能な形式的アーキテクチャモデルを持つ、(2) 名前空間・パッケージ間の循環は避ける、(3) ファイル・クラスの cycle group は5要素以下に抑える、(4) コピペ重複を避ける、(5) ファイルは800 LoC（ソフト）、(6) 最大インデント4・Modified Cyclomatic Complexity 15（ソフト）。既存コードはまず悪化を止め、月次・四半期で違反を数%ずつ減らす。余力がなければ循環依存の制限だけから始める［第9章 pp.168–169］

### 用語

- metrics-based feedback loop（目標設定→実装→継続的検証→改善の循環）
- structural erosion / entropy（構造の劣化。行き着く先が big ball of mud）
- big ball of mud（構造的なまとまりを失い密結合したコードベース）
- cycle group（循環依存で互いに到達できる要素の集合。強連結成分）
- dependency inversion principle（インターフェースを介して依存の向きを反転する原則）
- ACD / CCD（Average / Cumulative Component Dependency。依存の推移的な広がり）
- Propagation Cost（変更が波及しうる要素の平均割合）
- Fan In / Fan Out（被依存・依存の広がりを全体数で正規化した値）
- Relative Cyclicity（循環の大きさを正規化した指標）
- Structural Debt Index（循環を解消する作業量の推定値）
- Maintainability Level（著者の実験的な保守性指標）
- Cyclomatic Complexity（実行経路の数。テストケース数の下限）
- code churn（期間内に追加・削除された行数）
- hotspot（複雑で頻繁に変更されるファイル）
- LCOM4（クラスの凝集度の欠如を連結成分数で測る指標）
- hard / soft threshold（違反でビルドを止めるか、警告だけか）

### 解釈・実務への示唆

- 既存のコードに入れるなら、まず循環依存の制限だけを入れ、悪化を止めてから段階的にしきい値を締める。
- 違反でビルドを止める hard threshold と、警告だけの soft threshold を分ける。止めるのは直さないと困るものに絞る。
- ファイル 800 行、Cyclomatic Complexity 15 などの値は著者の経験に基づく目安で、言語や規模ごとの妥当性は未確認。

## 第10章 Goal-Question-Metric で未知のものを測る

原題: *Measure the Unknown with the Goal-Question-Metric Approach*／著者: Michael Keeling

### 章の問い

技術的負債の量や品質特性の充足度のように、直接測りにくい問いに対して、どうやって筋の良いメトリクスとデータ収集計画を導くか。

### 本の記述

- GQM は Basili と Weiss が提案した分析手法で、学びやすく適用しやすい。一人でも共同ワークショップでも使える。核となる前提は「何のために測るかを理解して初めてよく測れる」こと。理由を理解したチームはメトリクスを信頼し、意思決定に使いやすい［第10章 pp.171–172］
- GQM は階層構造（木）: 根が goal、枝が question、さらに metric、葉が計算に使う data。どのデータからも収集目的までたどれる traceability が得られる［第10章 p.172］
- goal の文は、目的、測定対象、関心事、視点（誰から見てか）を含むのが理想。例: ユーザー視点で可用性を上げる、PM 視点で新規マイクロサービスの開発時間を減らす、開発者視点でアーキテクチャの技術的負債を減らす。対象はアーキテクチャ、プロセス、実験、設計成果物、チームや組織でもよい。goal は分析中に見直してよく、不完全でも本質を捉えていれば役に立つ［第10章 pp.172–173］
- question は進捗（goal に近づいているか）を評価できる、運用に即したものにする。今すぐ答え方が分からなくても聞くべき問いを出す。可用性の例: 現在の可用性、最良・最悪のコンポーネント、よく落ちるもの、落ちる理由、典型的な障害時間、障害の時間帯［第10章 p.173］
- metric はルーブリック、Boolean、統計的推定、数式など何でもよいが、最終的には明確な定義が要る。各 metric は少なくとも一つの question に結びつき、一つの metric が複数の question に答えることも、一つの question に複数の metric が要ることもある。G→Q→M の3段の後、データの集め方を決める必要がある［第10章 pp.173–174］
- 優先順位づけ: 強いシグナルを出し、計算が安い metric を優先。複数の question に答える metric を探し、一つの question に重複する metric は本当に全部必要か検討する。成功を示す正の metric と失敗を示す負の metric の両方を入れる。データも木に加え、多くの metric に使われ、安く集められるデータを最優先にする［第10章 pp.174–175］
- データ源は、コードの計装、プロセスなら調査やタスク DB、コードならリポジトリや静的解析、短期実験なら数日の手作業収集など。全 metric を計算する必要はなく、作業（記録、収集、計算、ダッシュボード）を決めて計画を共有し実行する［第10章 pp.176–177］
- 事例の背景: 外部の Foo Service（仮名）は契約で時間単位・日単位の API レート上限を課し、超えると拒否する。システムはキューで処理量を管理し、一時障害後もキューとワーカーが動いていれば最終的に正しい状態に戻る self-correction を重視していた［第10章 pp.177–178］
- 障害1: 月曜未明、週末のバッチがストレージ障害とバグの組み合わせで過剰にリトライし、システム全体で共有するレート上限を超えた。複数コンポーネントが同時に影響を受け、数時間でキュー滞留が急増した。ポストモーテムでバグ修正に加え「もっと早く気づけたか」を問うために GQM を使った［第10章 p.179］
- goal は「Foo Service に関わる問題をユーザーに影響する前に発見し、緩和・解決する」。約30分の共有ドキュメントでのブレインストーミングで、question と metric を整理した。例: 現在の API 使用量、上限までの残り（全体と、コンポーネントごとの割り当てに対する残量の%）、相手側の問題か接続の問題か（エラー許容つきの heartbeat 成否、合成トラフィックの同期、15分窓のタイムアウト率・認証エラー率）、ジョブは正常か（リクエスト総数、正常・エラー・タイムアウト件数、15分窓のエラー率）、負荷に追いついているか（キュー深さとその平均、平均・p95・p99 の処理時間、スループット）［第10章 pp.179–180］
- データ収集を考える過程でアーキテクチャの欠陥が3つ見つかった: 負荷があるときしかデータが記録されない、失敗とリトライの責務が未割り当て、対応手順が不明確［第10章 p.180］
- 対策: Foo Service の metering API（使用量を確認できる）を使う heartbeat コンポーネントを追加。失敗処理の責務をジョブからワークキューへ移し、ジョブは fail fast とし、ADR に記録した。以前は一部のジョブが自前でリトライしており、最悪5回失敗×10回再投入で50リクエストになっていた。さらにメトリクスに基づくアラート、メトリクスを参照する runbook、診断用 API とツールを整備した［第10章 p.181］
- 障害2: 約9か月後の金曜未明、Foo Service 側の設定変更で14時間の全面停止が起きた。チームは10分以内にアラートを受け、診断 API で相手側の問題と確認し、一部のアラームを止め、ADR どおり exponential backoff でリトライされていることをメトリクスで確認した。ユーザーが気づく前に社内ユーザーへメールで告知し、復旧後はシステムが自己修正した。以前なら最優先障害だったものが小さな出来事になった［第10章 pp.181–182］
- 振り返り: メトリクスとその計算に必要なデータを具体的に考えることで、運用の可視性だけでなくアーキテクチャの欠落（データ収集のための部品、リトライ責務）が露わになった。ポストモーテムで GQM を使うと弱点の指摘と改善の道筋の両方が得られる［第10章 p.182］
- ワークショップ: 目的はメトリクスとデータへの合意と共同所有。参加者は2〜5人が最適（多ければブレイクアウト）、ソフトウェア開発者を最低1人、目的に応じて業務の専門家やプロダクト・マーケティング・営業も入れる。準備は goal の草案とホワイトボード（リモートなら Miro や共有ドキュメント）。成果物は合意された goal、question の一覧、question への参照つきの優先順位づけされた metric、metric の定義、必要データの一覧［第10章 pp.182–183］
- 手順: (1) 趣旨とグラウンドルールの共有、(2) goal を見える所に書く、(3) question を出す、(4) question ごとに metric をブレストし、答えられる全 question に線を引く（この段階ではデータの取り方は気にしない）、(5) goal に立ち返って妥当性を確認し、必要なら言い直す、(6) 必要データを特定し metric を精密化、(7) 優先順位づけ（must-have、複数 question に効くもの、ドット投票、価値／労力のどれか一つ）、(8) 振り返り、(9) 結果を記録して共有［第10章 p.184］
- 進行のコツ: 付箋1枚に1問で出し、読み上げてクラスタリングと重複除去。行き詰まったらデータの取り方はいったん忘れてもらう。metric やデータの再利用を探す。システム寄りの問いではアーキテクチャに詳しい人を入れてデータ収集コストを見積もる。GQM 木は写真に撮って共有する。不正調査の対象抽出を目的にした例では、ワークショップ後に facilitator が metric を精密に定義し、別の会議で優先順位をつけ、データ収集と計算がシステム要件になった［第10章 pp.185–186］
- 結論: メトリクス単体は「何かがおかしい」ことしか教えず、どうすべきかは教えない。GQM がその解釈の文脈を与える。分析、チームのコーチング、利害関係者の合意形成に使え、OKR 策定や技術的負債の判断にも応用できる。よく分かっていないものを測る場面でこそ役立つ［第10章 pp.186–187］

### 用語

- GQM（Goal-Question-Metric。目的から問い、指標へと分解する測定設計の手法）
- GQM tree（goal を根、question・metric を枝、data を葉とする木。traceability を与える）
- traceability（収集データから測定目的までたどれること）
- positive / negative metrics（成功を示す指標と失敗を示す指標）
- rate limit（一定時間あたりの API 呼び出し上限）
- heartbeat（定期的な疎通確認）
- synthetic traffic（監視のために人工的に発生させるリクエスト）
- queue depth（キューに滞留している未処理・処理中ジョブ数）
- p95 / p99（処理時間の95・99パーセンタイル）
- fail fast（失敗をすぐ返し、自前で粘らない設計）
- exponential backoff（リトライ間隔を指数的に伸ばす方式）
- ADR（Architecture Decision Record。設計判断の記録）
- runbook（障害時の対応手順書）
- postmortem（障害後の振り返り）

### 解釈・実務への示唆

- 指標を選ぶ前に goal を書き、question を経由させる。そうすると、どのデータが何の判断に使われるかをたどれる。[ログ設計の原則](../../logging/principles.md)の「何に答えるための記録か」から考える進め方と同じ形をしている。
- 必要なデータを具体的に書き出す段階で、設計の欠落（負荷がないとデータが出ない、リトライの責務が決まっていない）が見つかる。指標づくりは設計レビューの一部として使える。
- 成功を示す指標と失敗を示す指標を両方入れる。片方だけでは、良くなったのか、数え漏れなのかを区別できない。
