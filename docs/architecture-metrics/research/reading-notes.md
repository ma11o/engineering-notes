## 1. なぜアーキテクチャを測るのか

### 本の記述

- アーキテクチャ上の重要な判断の多くは品質特性（性能、回復力、セキュリティなど）に関わり、品質同士のトレードオフを伴う。continuous architecture などの進め方は、設計を最初に固めず、情報が揃った後で判断する。この進め方では、アーキテクチャの作業をどこまでやれば十分か、重要なことに時間を使えているかが分かりにくい。それを判断する手段が測定である。［第7章 pp.105–106］
- 一時点の測定は現在地を、時系列の測定はトレンドと向かう先を示す。測定を後回しにせず、作りながら測り、その結果で次に注意を向ける先を決める。［第7章 pp.106–107］
- アーキテクチャの品質の判断は、曖昧で主観的になりやすい。［第3章 p.43］
- アーキテクトは何十年も指標を使ってきたが、場当たり的だった。指標は、有用な文脈で継続的に評価されて初めてエンジニアリングの実践になる。［第8章 p.125］

### 解釈・実務への示唆

測定の役割は、設計の良し悪しの議論を値で確かめられる形にし、次に何を直すかを決めることにある。後で設計を見直すときは、次の問いに答えられるかを確かめたい。

- いまの設計判断は、どの品質特性を優先し、どれを犠牲にしたものか。
- その品質特性が十分かどうかを、何の値で確かめるか。
- 値が悪化したら、誰が何をするか。

3つ目に答えられない測定は、集めても使われない（第10・12節も参照）。

## 2. 何を測るかを決める: 目的から問い、指標へ

### 本の記述

- GQM（Goal-Question-Metric）は、goal を根、question を枝、metric をその先、data を葉とする木で測定を設計する。どのデータからも収集の目的までたどれる。核となる前提は「何のために測るかを理解して初めてよく測れる」こと。［第10章 pp.171–172］
- goal は、目的・測定対象・関心事・視点（誰から見てか）を含めて書く。例: ユーザーから見た可用性を上げる、開発者から見たアーキテクチャの技術的負債を減らす。分析中に書き直してよい。［第10章 pp.172–173］
- question は、goal に近づいているかを判断できる形にする。いま答え方が分からなくても、聞くべき問いは出す。metric は Boolean、統計的推定、ルーブリックなど何でもよいが、定義は明確にし、少なくとも一つの question に結びつける。［第10章 pp.173–174］
- 優先するのは、問いへの答えをはっきり示し（強いシグナル）、計算が安く、複数の question に答える metric。成功を示す指標と失敗を示す指標の両方を入れる。データも、多くの metric に使われ安く集められるものから集める。［第10章 pp.174–177］
- KPI Value Tree は、組織 KPI（EBITDA：利払い・税・償却前の利益、MAU：月間の利用者数 など）→ ドメイン KPI（契約の有効化率など）→ 指標（見積もりにかかる時間、deployment frequency など）を3階層でつなぐ。上位は結果を後から示す lagging indicator、下位には先行して動く leading indicator が入る。木は作った時点の姿にすぎないので、KPI と指標が役立っているかを話し合い、作り直し続ける。［第6章 pp.95–97］
- アーキテクチャは組織の使命と KPI につながっている必要があり、KPI が曖昧だとアーキテクチャは KPI と食い違う。［第6章 pp.87–88］
- 測りやすさではなく、影響の大きさで測るものを選ぶ。何でも集めるより、行動につながるものから小さく始める。［第7章 pp.118–119］

### 解釈・実務への示唆

GQM と KPI Value Tree は、どちらも「目的から指標へ木の形で分解する」点で同じ道具として扱える。違いは出発点で、GQM は一つの関心事（障害を早く見つけたい、など）から、KPI Value Tree は組織の数字から始める。

goal の視点（誰から見てか）を変えると、同じシステムでも木が変わる。[共通例1](../../logging/example.md)では「開発者から見て、レポート出力の失敗に早く気づく」が goal になり、question は「失敗したジョブはいつ、どれだけあるか」になる。[共通例2](../../logging/example-reservation.md)では「利用者から見て、予約できるはずの日を選べる」が goal になり、question は「条件を満たすのに一覧に出なかった日はあるか」になる。

指標を足すときは、木のどの question に答えるかを書き添えたい。答える question のない指標は、測りやすいから入ったものである可能性が高い。逆に、答えるべき question に指標がひとつもなければ、そこが測定の抜けになる。

成功と失敗の両方を入れるという指摘は、件数を数える指標で特に効く。共通例1で失敗したジョブ（`export.completed` の `outcome=failure`）の件数だけを見ていると、件数が減ったのが改善なのか、ジョブ自体が減ったのか区別できない。全件数と並べて、失敗率で見る。

## 3. 測定の種類と手段

### 本の記述

測定は、成果物（artifact）を測るか稼働中のシステム（operational）を測るか、チームの外から見えるか（external）内側か（internal）で4種に分けられる。［第7章 pp.107–108］

| 種類 | 例 | 長所と限界 |
| --- | --- | --- |
| external artifact | 設計文書による標準（GDPR など）への準拠の評価 | 最初期にでき、関係者の信頼を得やすい。判断に頼るので最も弱い |
| internal artifact | コードの複雑度、モジュールの結合度、スキーマ要素数 | 正確で安い。成果物ができるまで測れない |
| external operational | 応答時間、throughput、復旧時間、月あたり障害数 | 利用者の体験を捉える。本番稼働が要る |
| internal operational | メモリ使用量、データ量に対するインデックスの伸び | 将来の問題の予測に役立つ |

手段は5つある。［第7章 pp.108–110］

- 実行時の測定: logs・traces・metrics。インフラ側はクラウドの基盤で取りやすいが、アプリ側は自前の実装や APM（アプリの処理時間やエラーを計測する製品）が要る。その分、売上のような関係者が本当に気にする情報を取れる。
- ソフトウェア解析: 静的解析は誤りと構造（複雑度、結合度）を測るが、保守性以外の品質はあまり評価できない。
- 設計解析: 実装前の最小限の設計表現から、標準への準拠やスケーラビリティを予測する。
- 見積もりとモデル: 過去の測定値やベンチマークから、運用パラメータと品質の関係を表計算でモデル化する。性能・スケーラビリティ向き。
- fitness function: 新しい測定手段ではなく、測定値を使って品質が許容範囲にあるかを監視する仕組み（第4節）。

### 解釈・実務への示唆

4分類は、測定の抜けを見つける枠として使える。開発チームが自然に集めるのは internal artifact（静的解析）と internal operational（リソース監視）に偏りやすく、利用者が体験する external operational が後回しになりやすい。

ログ・トレース・メトリクスは、この分類では operational な測定の手段にあたる。何を記録するかを「何に答えるための記録か」から決める[ログ設計の原則](../../logging/principles.md)は、第2節の GQM と同じ形をしている。

## 4. fitness function: 指標を設計の検証に変える

### 本の記述

- fitness function は *Building Evolutionary Architectures* の概念で、アーキテクチャ特性を客観的に評価する基準を与えるあらゆる仕組みを指す。名前は遺伝的アルゴリズムで解の良さを判定する目的関数に由来する。［第8章 pp.125–126、第2章 p.21］
- fitness function は、目標の指標と、その前提になる文脈（環境、定義、制約）を定める。architectural test がその指標を測り、しきい値と照合する。定義は設計時に決め、テストは後から実装する。［第2章 pp.22–23］
- 書き方の例: 単体テストのカバレッジ90%超を CI ビルドごとに検証し、下回ればビルドを失敗させる。外部 API に10秒の遅延を注入しても統合テストのエラーが0%で、実行時間が通常の2倍を超えないこと。［第2章 pp.23–24］
- 単体テストからコードの指標、運用の監視、chaos engineering まで、検証の道具は散らばっていた。どれも fitness function として、同じ考え方で扱える。［第8章 pp.126–127］
- 客観的に測れないと検証できない。測り方が分からない特性（reliability など）は複合特性（測れる複数の特性が組み合わさったもの）であり、さらに分解すべき合図である。［第8章 pp.126–127］
- ダッシュボードに並ぶだけで、しきい値を決めて定期的に実行しない指標では、設計が崩れたことが後から分かるだけである。変更のたびに自動で実行して初めて予防になる。［第8章 p.127］
- 自動化が理想だが、表計算のような手動の fitness function にも価値がある。［第7章 p.110、第2章 pp.21–22］
- 作り込みすぎて開発者を苛立たせない。fitness function は、「重要だが緊急ではない」原則を実行できるチェックリストにしたものである。緊急の作業に追われると、こうした原則は後回しにされ、技術的負債になる。継続して実行する fitness function にしておけば、開発者が飛ばせない。［第8章 pp.141–142］

### 解釈・実務への示唆

fitness function は「指標・しきい値・いつどこで実行するか・外れたらどうするか」の4つを決めたものと読むと扱いやすい。指標だけを決めたら、残りの3つを決めて fitness function にする。

「測り方が分からないなら複合特性なので分解する」という考え方は、曖昧な品質目標を扱うときに使える。たとえば共通例1のレポート出力ジョブを「運用しやすい」状態に保つ、という目標は、そのままでは検証できない。失敗に気づくまでの時間、キュー待ちの時間（`queue_wait_ms`）、再試行で成功したジョブの割合（`recovered=true`）に分けると測れるようになる。

手動の fitness function を認めている点も重要である。最初から自動化を目指すと、作れないまま止まりやすい。手で測る形から始め、値が安定してから自動化と、ビルドを止める強さに上げていけばよい（第5節）。

## 5. どこから作るか: 分類とピラミッド

### 本の記述

- 必須の分類は6つ: フィードバックの広さ（atomic：一つの部品だけを見る／holistic：複数の部品の組み合わせを見る）、実行の契機（triggered：変更などをきっかけに実行する／continual：本番で常に実行する）、実行場所（CI/CD、テスト環境、本番）、指標の型（真偽、離散値、時系列）、自動／手動、品質特性。最も重要なのは品質特性。任意の分類は、一時的／恒久的、静的／動的、対象読者、適用範囲。［第2章 pp.25–30］
- 品質特性の例として ISO/IEC 25010 の8特性（機能適合性、性能効率性、互換性、使用性、信頼性、セキュリティ、保守性、移植性）を使う。［第2章 pp.27–28］
- 層は主に広さと契機の組み合わせで決まる。下層は triggered atomic（カバレッジ、循環的複雑度）、中層は triggered holistic か continual atomic（夜間の統合テスト、本番の処理時間の監視）、上層は holistic のみ（本番の売上や checkout 率の監視、chaos engineering）。上層ほど現実に近いが、高価で非決定的（同じ条件でも結果が変わる）になりやすいので数を絞る。［第2章 pp.32–35］
- 上層の例: 時間帯ごとに1分あたり売上の下限を設け、本番で常時検証する。深夜のローリングデプロイ中に主要な5つのユースケースを流し続け、100ms 以内に応答することを確かめる。［第2章 pp.37–39］
- 作り方は7手順: 品質目標をステークホルダーと合意する → 下書きをバックログに置く → 重要で今作れるものを選ぶ（最初は下層から）→ 定義と分類を確定する → 自動テストを作る → ダッシュボードで見せる → 定期的に見直し、不要なものを廃止し、しきい値を調整する。［第2章 pp.39–41］
- 最初から全部は分からないので、小さく始めて学びながら足す。簡単だからという理由で目標と無関係なテストを自動化するのは典型的な失敗。［第2章 p.40］
- 既存のシステムには、緩い目標から入れて段階的に締める。いきなり標準の目標を当てると違反が大量に出て士気が下がる。［第9章 pp.143–144］
- 自動化できない検証は一時的に手動でもよいが、繰り返す作業はすぐ自動化する。［第5章 pp.70–71、78］

### 解釈・実務への示唆

分類表は、新しく作るときより、今あるテストと監視を棚卸しするときに役立つ。表の列に広さ・契機・場所・品質特性を並べて既存のものを埋めると、「CI の静的チェックはあるが、本番で利用者の体験を見るものがない」のように手薄な層が見える。

強さの段階も分けておきたい。記録するだけ → 警告する → ビルドやデプロイを止める、の順に上げる。第7章の事例でも、値が不安定な脆弱性の指標はトレンドを見るだけの指標として扱っている（第7章 pp.119–121）。止める段階に上げるのは、誤検知が少なく、外れたら必ず直すものに限るのがよい。

## 6. デプロイの速さと安定性: four key metrics

### 本の記述

- four key metrics は、変更がバージョン管理に入ってから本番で動くまでを一本のパイプとして見るモデルから生まれる。デプロイ頻度と変更のリードタイムがスループット、変更失敗率とサービス復旧時間が安定性を表し、4つを組み合わせて見る。［第1章 pp.2–3］
- 対象範囲（インフラの変更を含むかなど）は4指標で揃える。数えるのは利用者に変更を届ける成功したデプロイだけで、途中で失敗したビルドを含めるとリードタイムが短く見える。［第1章 pp.3, 8］
- 計測点は4つの時刻: コミット（妥協として main へのマージでもよい）、本番デプロイの完了、障害の起票、障害のクローズ。［第1章 pp.6–9］
- 障害は「利用者が目的の作業を完了できない、または続ける気をなくす状態」と定義する。復旧はロールバックでよく、根本原因の修正を待たない。［第1章 p.9］
- 集計は手作業から始めてよい。デプロイ頻度とリードタイムは直近31日の平均、復旧時間は直近120日の平均か中央値。未解決の障害は計算から外すが、件数は隠さず表示する。［第1章 pp.10–12］
- DORA の指標は速さと安定性の leading indicator として使えるが、文脈が違うチーム同士を比べるのは逆効果。モバイルアプリでは、リリースのたびに更新通知が出て利用者を煩わせ、評価（NPS）を下げる。そこで、alpha・beta・production の3段階（deployment ring）に分け、変更はすべて alpha に自動でデプロイして、いつでもデプロイできる能力を持つことにした。［第6章 pp.97–99］
- 可観測性が整っていれば、障害の発生から発見までの平均時間（mean time to discover）も使える。［第6章 pp.97–98］

### 解釈・実務への示唆

計測点はパイプラインの時刻と障害チケットの時刻だけなので、特別な仕組みがなくても始められる。難しいのは定義の方で、「何を1回のデプロイと数えるか」「何を障害と数えるか」を決めて公開しておく。そうすれば、値の上下を同じ前提で議論できる。

障害を利用者から見た結果で定義する点は、[レベル・結果・通知](../../logging/severity-and-outcomes.md)で処理の成否と例外を分けて考えるのと同じ考え方である。共通例2に当てはめると、予約可能日 API がエラーを返していなくても、判定の誤りで予約できるはずの日が一覧に出なければ、障害に数えることになる。

## 7. 保守性と構造の劣化

### 本の記述

- technical debt は2種類に分けられる。implementation debt（長いメソッドなどの code smell）はツールでほぼ自動検出できる。design and architecture debt（依存関係が計画と合わない）は数えるだけでは分からず、レビューが要る。［第4章 p.50］
- 拡張のたびに負債は生じるので、改善を定期的に挟めば保守コストを低く安定させられる。改善しないと architecture erosion が進み、単位時間あたりに作れる機能が減る。［第4章 pp.50–51］
- 保守性の最大の敵は構造の劣化（entropy）で、行き着く先が big ball of mud（全体が絡み合い、構造が見えなくなったコード）。目に見える兆候は、循環依存で結ばれた要素の塊（cycle group）が育つこと。Apache Cassandra では最大の塊が版ごとに約450 → 900超 → 1,300超ファイルに拡大した。［第9章 pp.144–146］
- 循環依存があると、単独でテストできず、理解しにくく、部品を切り出せない。dependency inversion principle などで必ず断ち切れる。小さいうちなら直すのは簡単。［第9章 pp.146–148］
- MMI（Modularity Maturity Index）は、modularity 45%・hierarchy 30%・pattern consistency 25% の重みで 0〜10 に評価する。8以上は良好、4〜8はリファクタリング、4未満は置き換えを検討する。［第4章 pp.57–61］
- 推奨しきい値の例: 最大の cycle group は5要素まで、パッケージ間の循環はゼロ、ファイルは約800行、Cyclomatic Complexity は15、最大インデントは4。［第9章 pp.147–148、153、160–162］
- 規模によって指標の読み方が変わる。変更が波及しうる割合（Propagation Cost）は、部品数が500未満なら高くても問題になりにくく、5,000以上なら10%でも懸念になる。［第9章 p.152］
- 変更履歴も手がかりになる。複雑で頻繁に変わるファイル（hotspot）はリファクタリングの候補で、一人しか触っていないファイルは知識の独占のリスクを示す。［第9章 pp.162–163］
- 優先する特性は最大3つと保守性に絞る。CI で毎日測ってトレンドを追い、違反でビルドを止める hard threshold と、警告だけの soft threshold を分ける。［第9章 pp.165–167］
- 変えやすさの性質（modularity、cohesion、separation of concerns、abstraction、coupling）は、テストしやすいコードの条件と一致する。だからテストのしやすさを設計の指針にできる。［第3章 pp.44–46］

### 解釈・実務への示唆

負債の2分類は、点検の分担にそのまま使える。implementation debt は CI の静的解析に任せ、design debt は目標の構造と実際の依存関係を突き合わせるレビューで見る（第4章 pp.61–63）。

既存のコードに最初に入れるなら、循環依存の制限だけで十分である。第9章も、余力がなければ循環の制限から始め、まず悪化を止めてから違反を少しずつ減らすよう勧めている（第9章 pp.168–169）。MMI や Maintainability Level（第9章の著者が作った、依存関係から保守性を%で表す指標）のような合成した点数は、他のシステムと比べたいときや、置き換えを判断したいときに使う。

テストが書きにくいと感じたら、それを結合や関心の分け方を見直す合図として扱える。指標を入れていない段階でも使える目安である。

## 8. 品質特性ごとの測り方

### 本の記述

| 品質特性 | 測り方 | 落とし穴 | 出典 |
| --- | --- | --- | --- |
| 性能 | latency（1件の処理時間）と throughput（一定時間の処理件数）。応答時間は1回ではなく、平均・中央値・ばらつきで分布として見る | テスト環境と本番の差、現実的な負荷を作る難しさ、分散システムの間欠的な現象、ログの不足と過多 | 第7章 pp.111–112 |
| スケーラビリティ | 資源を増やしたときに処理能力がどう伸びるか。例: 応答時間の条件を満たして処理できる件数を、資源を20%ずつ増やして測る。資源のコストや運用に必要な人数も対象 | 予期しないボトルネックと非線形の振る舞い、複数の資源の組み合わせ | 第7章 pp.113–114 |
| 可用性 | MTBF（障害の間隔）と MTTR（復旧時間）。MTTR は設計・テストできるが、MTBF は推定しにくい。データの損失は RPO（失ってよい量）と RTO（使えるまで待てる時間）で表す | 構成要素ごとの値の合成、nines（99.99% など）は障害の種類や時間帯を無視している | 第7章 pp.114–116 |
| セキュリティ | インシデント数を待たず、静的解析・ペネトレーションテスト・インフラスキャンの結果を、発生可能性と影響で重み付けして集計する | 環境の構成差、誤検知、重み付けの難しさ | 第7章 pp.116–118 |
| 保守性 | 第7節を参照 | — | 第4・9章 |

### 解釈・実務への示唆

可用性の要件は、nines の値から決めるより、どんな障害がいつ起きたら業務が困るかのシナリオから決めたい。同じ1分の停止でも、共通例2の予約可能日 API なら、予約の受付が始まった直後と深夜とでは影響が違う。

セキュリティの指標が「セキュリティそのもの」ではなく「テスト結果の集計」だという整理は、他の品質特性にも当てはまる。直接測れないものを代わりの値で測るときは、その値が何の代わりなのかを指標の定義に書いておくと、値だけが独り歩きしにくい。

## 9. 指標の読み方: 組み合わせと推移

### 本の記述

- スループットを上げても安定性が下がれば偏った改善で、長続きしない。4指標は常に一緒に見る。［第1章 p.3］
- 間接指標（問題の兆候だけを示す指標）は問題の存在を示すが、原因は示さない。［第5章 p.76］
- 第5章は、フィードバックまでの時間、避けられた統合不具合の数、本線の復旧にかかった時間の3指標を組み合わせて状況を推測する。例: フィードバックが遅く避けられた不具合も多ければ、検証が CI と QA に偏り、手元で捕まえずに本線へ入れている。不具合は少ないのに本線の復旧に時間がかかれば、メンバー間で手元の検証の規律に差がある。［第5章 pp.78–79］
- 値より推移が重要なことがある。mean time to discover の悪化は、設計の複雑化による従業員のエンゲージメント低下を示しうる。mean time to discover と change fail rate を組み合わせると弱点が見つかる。［第6章 pp.103–104］
- 表示では、繰り返し出る問いに答える文脈を足す。たとえばリードタイムのグラフにその日のデプロイ数を重ねて、「その日はデプロイが多かったか」にすぐ答えられるようにした。［第1章 pp.13–17］

### 解釈・実務への示唆

一つの指標が悪化したとき、すぐに原因を決めず、「この値が悪化する理由は何通りあるか」を挙げ、それを見分ける別の指標を並べたい。第5章の組み合わせ表はその作業を先にやっておいたものと読める。共通例1でジョブの所要時間が悪化したら、キュー待ち（`queue_wait_ms`）が伸びたのか、PDF 生成の呼び出し（`renderer.attempt_completed` の `duration_ms`）が遅くなったのかを並べて見分ける。

推移を見るには、定義を途中で変えないことが前提になる。定義やルールを変えたときは、変えた日をグラフに書き込んでおく。共通例2で予約の判定ルールを `rule_version` v1 から v2 に変えた日に予約可能日の件数が減っても、障害と取り違えずに済む。

## 10. 指標をチームと組織で使う

### 本の記述

- 生データ、計算、各指標の定義をすべて公開する。最初は wiki ページに、現在値・定義と集計期間・過去の値・データの出所を載せれば十分。［第1章 p.12］
- 主な読み手は、ソフトウェアを届けるチーム。経営層には集約した値を読み取り専用で見せ、詳細はチームに聞きに来てもらう。［第1章 p.13］
- 毎週、ADR とともに指標を議論すると、会話は意味 → なぜこの値か → どう改善するかへ進み、チームが自ら改善を始める。やがて結合の強さや観測しにくさなど、アーキテクチャの問題が表に出る。［第1章 pp.18–19］
- KPI や指標は目標ではなく道しるべとして使う（Goodhart's Law）。「KPI X を達成できていない」という言い方が出たら目標化のサイン。目標が要るなら、目標と呼び分ける。［第6章 p.97］
- 指標が普及しない理由: 教育で扱われない、ツールがニッチ、文脈と専門性が要る（誤った指標を選ぶと、指標を満たすだけの表面的な改善になる）、ルールが多すぎる（適量は5〜6個）、負債で改善の余力がない。［第9章 pp.148–149］
- 自動化と検証を別チームに任せきると、開発チームは本線が壊れても直せなくなる（ownership shift）。検証の重心を手元の開発環境に戻し、push 前に統合を確かめる private build を行う。［第5章 pp.68–71］
- 測った結果で行動する。スプリントの一定割合を測定結果への対応に充てる、という案もある。［第7章 pp.121–122］

### 解釈・実務への示唆

指標を誰が見て、誰が直すのかを先に決めたい。直す人が見ていない指標は改善につながらず、見ている人が直せない指標は、責める材料になりやすい。第1章が届けるチームを主な読み手にしているのは、この2つを一致させるためと読める。

目標と道しるべを呼び分ける規則は、そのまま使える。SLO のように外れたら対応すると約束しているものは目標、DORA の4指標のように傾向を見て会話するものは道しるべ、と分けておくと、ダッシュボードの値に対する反応が揃う。

## 11. 測ると設計の穴が見える: 事例

### 本の記述

- 外部 API の利用上限を超えた障害の後、「もっと早く気づけたか」を GQM で分析した。必要なデータを考える過程で、負荷があるときしか記録が残らないこと、失敗とリトライの責務が決まっていないことが分かった。一部のジョブが自前でリトライし、最悪50回の呼び出しに膨らんでいた。［第10章 pp.179–181］
- 対策として、利用量を確認する heartbeat の部品を足し、リトライの責務をキューに移して ADR に記録し、指標に基づくアラートと手順書を整えた。9か月後に相手側で14時間の停止が起きたときは10分以内に気づき、利用者が気づく前に告知でき、復旧後はシステムが自己修正した。［第10章 pp.181–182］
- EC の在庫補充で、仕入先を計算する API の失敗を補充対象の商品と結びつける指標を作ると、供給が終わったのにシステム上は廃番になっていない商品が原因と分かった。直すと API のエラーはほぼゼロになった。［第6章 pp.101–102］
- オーケストレータ型のマイクロサービスで「ドメインサービスはオーケストレータとしか通信しない」という規則を、直近24時間の呼び出しログを読んで検証する fitness function を自作できる。［第8章 pp.134–135］
- GitHub はマージ処理を書き換える際、旧実装の結果を返しつつ新実装をリクエストの1%で並走させて結果を比べる Scientist を作った。4日間で1,000万回超の比較を行い、不一致のない状態を確かめてから旧実装を消した。［第8章 pp.138–141］
- Equifax の侵害は、脆弱性の公表から一部システムへのパッチ適用までに数か月かかったことで起きた。全プロジェクトにデプロイパイプラインがあれば、特定バージョンのライブラリを検出してビルドを止める fitness function を差し込めた。［第8章 pp.136–137］

### 解釈・実務への示唆

第10章と第6章の事例に共通するのは、指標を作ろうとしてデータの取り方を具体的に考えた時点で、設計の穴が見つかったことである。指標づくりは、監視を整える作業であると同時に、設計レビューとしても使える。

共通例1にも同じ穴がありうる。ワーカーは最大3回まで試行するが、キューにもメッセージの再配信の仕組みがあれば、PDF 生成サービスへの呼び出しは3回を超えうる。呼び出し回数（`attempt_count`）を指標にしようとした時点で、リトライの責務をどちらが持つかを決めることになる。

第8章の2つの事例は、ログが fitness function の入力になりうることを示している。呼び出し先を構造化して記録しておけば、アーキテクチャの規則違反の検出に使える。新旧実装の比較では、「一致・不一致・新実装の例外」を区別して記録することが前提になる。

| アンチパターン | 問題 | 出典 |
| --- | --- | --- |

## 13. 補足: ADR（設計判断の記録）

第1章と第10章に ADR（Architecture Decision Record：設計判断を一件ずつ短い文書に残したもの）が出てくる。ただし本は、ADR の書き方や運用を扱っていない。ここでは本の記述と、一次資料で確かめた一般的な運用を分けて置く。

### 本の記述

- 第1章のチームは毎週集まり、これから行う spike（技術検証）と ADR を議論し、four key metrics を見ていた。ADR という言葉は Michael Nygard が考えた。［第1章 p.18］
- 第10章のチームは、障害の分析を受けて「ジョブはすぐに失敗させ、リトライはキューに任せる」と決め、ADR に記録した。次の障害では、ADR に書いたとおり指数バックオフで再試行されていることを、指標で確かめた。［第10章 p.181］

### 一次資料での運用

2026-10-10 に次の資料で確認した。

- Michael Nygard, [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)（2011-11-15）
- [MADR](https://adr.github.io/madr/)（Markdown Architectural Decision Records）4.0.0（2024-09-17 リリース）
- AWS Prescriptive Guidance, [ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)
- Microsoft Azure Well-Architected Framework, [Maintain an architecture decision record](https://learn.microsoft.com/en-us/azure/well-architected/architect-role/architecture-decision-record)（2026-04-13 更新）

| 問い | 資料での扱い |
| --- | --- |
| 何のために書くか | 判断の理由が残っていないと、後から来た人は、その判断をそのまま受け入れるか、知らずに覆すかしか選べない。それを避ける（Nygard） |
| どの判断を書くか | 構造、非機能特性、依存関係、インターフェース、構築の技法に影響する判断（Nygard）。元に戻しにくい判断も含め、退けた選択肢も残す（Microsoft） |
| 何を書くか | タイトル、Context（判断を左右する事情を、評価を交えず事実として書く）、Decision（「〜する」と能動態で書く）、Status、Consequences（良い結果だけでなく、すべての結果）。全体で1〜2ページ（Nygard）。MADR はこれに、検討した選択肢と、決定を守れているかの確かめ方（Confirmation）を加えたテンプレートを用意している |
| いつ書くか | 決める前に Proposed として書き、チームのレビューを経て Accepted にする（AWS）。システムを作り始めるときに記録を始め、運用する間は続ける。既存のシステムでは、分かる範囲で過去の判断をさかのぼって書く（Microsoft） |
| 誰が書くか | Nygard は役割を決めておらず、チーム（we）として書いている。AWS では、チームの誰でも書ける。書いた人が ADR owner として内容を保ち、周りに伝える。採用・差し戻し・却下はチームのレビューで決める。Microsoft は、ADR をソリューションアーキテクトの重要な成果物としている |
| 判断を変えるとき | 採用した ADR は書き換えない。新しい ADR を書き、古いほうを superseded（置き換え済み）にして、新しいほうへのリンクを残す（Nygard、AWS、Microsoft）。却下した ADR も理由とともに残し、同じ議論を繰り返さないようにする（AWS） |
| どこに置くか | リポジトリの `doc/arch/adr-NNN.md` に置き、番号は連番で再利用しない（Nygard）。MADR は `docs/decisions/NNNN-title-with-dashes.md` を勧めている |
| どう使うか | コードレビューやアーキテクチャレビューで参照する。ADR に反する変更には、その ADR へのリンクを添えて修正を求める（AWS） |

### 解釈・実務への示唆

ADR は、fitness function と組にすると生きる。第10章のチームも、ADR に書いた決定（リトライはキューに任せる）が守られていることを指標で確かめている。MADR の Confirmation に、決定を確かめる fitness function を書いておけば、「何を決めたか」と「守れているかをどう確かめるか」が一か所にそろう。

共通例1なら、「PDF 生成の再試行はワーカーが最大3回まで行う」を ADR に書き、`export.completed` の `attempt_count` が3を超えないことを fitness function で確かめる。超えたら、第11節で見たような、キューの再配信との重なりを疑う。

第1章のように、ADR と指標を同じ場で議論する形も使える。決めたことと、その後の値の動きを並べて見られるので、判断を見直す時期が分かる。

## 14. 実務と照合するときの問い

- この指標はどの goal と question に答えるか。答える question のない指標はないか。
- 品質特性ごとに、外から見える測定（利用者の体験）と内側の測定（コードやリソース）の両方があるか。
- 各指標に、しきい値・実行の契機・外れたときの対応が決まっているか。記録だけ・警告・ビルド停止のどの強さか。
- 指標の定義（何を1件と数えるか、対象範囲、集計期間）は公開されているか。
- 指標を見る人と、値を改善できる人は一致しているか。
- 悪化したとき、原因を見分けるための別の指標が並んでいるか。
- 目標として扱うもの（SLO など）と、道しるべとして扱うものを呼び分けているか。
- 重要な設計判断が ADR に残り、それを確かめる指標や fitness function と結びついているか。
- 使われなくなった測定を止める見直しの機会があるか。
