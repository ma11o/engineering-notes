# 技術ノートの日本語を整える

書籍や仕様を読んでまとめたノートは、原文の硬い言い回しや、正確さを守るための留保が残りやすい。読み手が「では何をすればよいか」をつかめる文に直す。**事実や主張の強さは変えない。**

リポジトリの `CLAUDE.md` の「書き方」「出典と事実確認」に従う。ここではその進め方を書く。

## 1. 読む

- 対象テーマの章をすべて読む（例: `docs/<テーマ>/` の本文）。`research/` の根拠資料は、依頼がなければ対象外にする
- テーマの `README.md` で、共通の前提・共通例・読む順番を確かめる
- 打ち消しの多さを数えて目安にする

```bash
for f in docs/<テーマ>/*.md; do printf "%s 打消し=%s 文=%s\n" $f $(grep -o -E "ではない|とは限らない|わけではない|ならない|できない" $f | wc -l) $(grep -o "。" $f | wc -l); done
```

## 2. 候補を洗い出す

次の観点で、直したほうがよい文を拾う。

| 観点 | 例 |
| --- | --- |
| 説明なしの専門用語・ノート独自の造語 | 「事前集約」「横断比較」 |
| 一文への詰め込み | 「識別子を含む収集候補にも、必要性と安全性の判断が別途要る」 |
| 何を指すか見えない抽象語 | 「文脈を将来へ渡す」「処理の構造を復元できない」 |
| 二重否定・打ち消しの連続 | 「〜を持てないという意味ではない」 |
| 留保の重ね・情報のない一文 | 「これらは採用側の設計判断であり、ID名だけから自動的には決まらない」 |
| 各章で繰り返す但し書き | 「これは説明用であり、採用規則ではない」 |

具体的な直し方は [references/examples.md](references/examples.md) にある。

## 3. 一覧を見せて、了承を得る

直す前に、ファイルごとに次の表で候補を見せる。冒頭に直し方の方針を書く。

| # | 行 | 現状 | 何が分かりにくいか → 直し方（案） |
| --- | --- | --- | --- |

- 番号を振り、外したいもの・言い回しを変えたいものを番号で返せるようにする
- 件数が多ければ、重要度の高いものから並べる
- ユーザーの返事を待ってから直す

## 4. 直す

- **一般的な専門用語は残す。** WAL、原子性（アトミック性）、SLO、span、カーディナリティのように、調べれば出てくる用語は言い換えない。言い換えると元の用語で調べられなくなる。初出で括弧に一言説明を添える
- **ノート独自の硬い言い回しは、平易な言葉に言い換える**
- **抽象的な説明は、テーマの共通例の具体的な値で言い直す。** 共通例がなければ、一つ決めて全章で使うことを提案する
- **長い文は二文に分け、結論を先に書く**
- **打ち消しは肯定の形にし、各節を「ではどうするか」で終える**
- **各章の冒頭に「要点」を3つ、言い切りの形で置く**
- **全章に共通する但し書きは、テーマの `README.md` にまとめて各章から削る**
- 情報のない一文は削る

## 5. 事実を変えない

- 書籍や仕様の記述を言い換えるときは、元の資料（書籍のページ、仕様の文言）で意味を確かめ直す。言い換えで意味が強まったり弱まったりしないようにする
  - 例: W3C Trace Context の `sampled` フラグを「トレースが保存されたことは保証しない」と書くより、仕様の文言どおり「呼び出し元がトレースを記録した可能性がある」と書く
- 留保を削るときは、それが事実の限定（仕様の成熟度、未確認であること、適用範囲）なのか、ただの重ね書きなのかを分ける。事実の限定は残す
- 自分の解釈を新たに書き足したら、報告でそう示す

## 6. 確かめて報告する

- `mkdocs build --strict` でリンク切れがないことを確かめる
- 打ち消しの数を直す前と比べる
- 何を直したか、何を残したか（理由つき）、自分の解釈を足した箇所を報告する
- コミット・push はユーザーの依頼に従う
