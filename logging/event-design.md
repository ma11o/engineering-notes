# イベントの設計：何が起きた一件なのか

**要点**

- 先に「どの出来事を、どの時点で一件とするか」を決める。処理全体と一回の試行は別の出来事にする
- イベント名は出来事の種類、毎回変わる値は属性。属性は型・単位・欠落時の意味まで決める
- 「完了」「成功」の記録は、どの事実が成立した後に出すかを定義する

構造化ログで最初に決めるのは、JSONのキー名ではなく、**どの出来事を、どの時点で一件として残すか**である。この定義が曖昧なら、整ったJSONでも検索結果や件数の意味が揃わない。

ここでいうイベントは観測用の記録。業務メッセージ、イベントソーシングの正本、配信保証のあるイベントと同じものではない。また、書籍で広く使うeventという語と、特定APIのSpan Eventも無条件には対応しない。

## 処理全体と、一回の試行を分ける

[共通例](example.md)の場面Bでは、レポート出力ジョブがPDF生成サービスを呼び、一回目のタイムアウト後、二回目で成功した。ジョブは一件、外部呼び出しは二回である。これらを全部「処理完了」として数えると、処理件数も失敗率も意味が変わる。

そこで、ジョブ全体の終了（`export.completed`）と、外部呼び出し一回の終了（`renderer.attempt_completed`）を別の出来事にする。書籍の `main` 属性は主要な処理を選ぶ一例だが、その名前を必須とする理由はない。重要なのは、集計時に同じ単位だけを選べることだ。

短い処理なら完了要約に文脈を集めやすい。長時間ジョブや途中停止を追いたい処理なら、開始や重要な中間状態も必要になる。進行中のspanを繰り返し保存し直す方法は多くの保存先が扱えないと書籍は説明しており、中間イベントやメトリクスと終了要約を組み合わせる方が適する場合がある。

## 名前は出来事の種類、属性はその回の値

共通例では、`export.completed` を「ジョブが成否にかかわらず終了した時点の記録」と定義している。`job_id` はそのジョブ、`outcome` は成否、`duration_ms` は所要時間を表す。この名前は成功を保証しない。成功だけに使うなら、発生条件をそう定義し直す。場面BをJSONで出すと次のようになる。

```json
{
  "event_name": "export.completed",
  "job_id": "job-1025",
  "outcome": "success",
  "attempt_count": 2,
  "recovered": true,
  "page_count": 12,
  "duration_ms": 3850,
  "service_version": "v2.3.0"
}
```

`export.job-1025.completed` のように個体IDを名前へ入れると、同種の出来事をまとめにくくなる。反対に、`message` に「1025番が3850msで成功」とだけ入れても、値の比較には文章解析が要る。人が読む説明文と、検索・集計する値を分けて考える。

出力側がJSONにしても、保存先が全体を一つの文字列として扱っていれば、属性ごとに比較する利点を十分には得られない。収集・変換を通ったあとも、保存先でフィールドと型が認識され、検索・集計に使えるかを確かめる。

## 属性は、型と意味まで契約にする

同じ `duration` でも秒とミリ秒が混在すれば比較できない。`0`、不明、未取得、該当しない状態も同じではない。名前だけでなく型・単位・欠落時の意味を決める。

集める文脈は、例えば次の問いから選べる。全項目が必須という意味ではない。

- どこで何が動いたか：サービス、環境、バージョン、実行場所
- どの条件だったか：ルート、入力の規模、Feature flag、キャッシュの利用結果
- どこに時間を使ったか：全体と主要工程の時間、依存先の呼び出し回数
- 何が成立したか：結果、失敗した工程、安定したエラー分類
- どことつながるか：現在のトレース、ジョブ、外部サービス側の識別子

URL、ユーザー識別子、例外文、外部レスポンスは、そのまま収集してよい情報とは限らない。[情報保護](security-and-privacy.md)と合わせて項目を選ぶ。

## 時刻と状態が、何を証明するか

「更新を試みた」「DBへコミットした」「応答を送った」は異なる出来事である。保存前に成功と書けば、後でロールバックしてもログだけ成功に見える。完了イベントは、どの事実の成立後に出すのかを決める。共通例の `export.completed` は、DBのジョブ状態をコミットした後に出す。

また、発生時刻と収集側が観測した時刻が異なる場合がある。送信遅延やクロックのずれがあれば、検索結果の並びだけから因果関係は決められない。時刻の意味と単位を揃え、処理の関係は[相関IDやトレース](correlation.md)も使って読む。

完了記録がない場合も、未完了とは限らない。停止、収集障害、サンプリング、保持期限などが考えられる。状態の成立と、その記録が検索できることを分ける必要がある。

## OTelを使うなら、モデルと意味規約を区別する

OpenTelemetryのLogRecordモデルでは、`EventName` はイベントの型、`Body` は本文、`Attributes` は付随する情報を表す。一般のBodyは文字列だけでなく構造化値も扱え、空でないEventNameを持つLogRecordがEventに当たる。すべてのログを名前付きEventにする必要はない。

これに対して、イベントのSemantic Conventionsは、名前に発生ごとの可変値を含めないこと、構造化した文脈を属性へ定義すること、Bodyの定義を表示用文字列に限ることなどを扱う。これは一般のLogRecordが構造化Bodyを持てないという意味ではない。

確認日時点では前者はStable、後者はDevelopmentであり、同じ成熟度ではない。仕様の要求はその仕様を採用する範囲に適用される。独自JSONの `event_name` や `message` を公式欄名へ置き換えただけでは、SDKから保存先までの適合性を示せない。

時点の発生や状態変化はEvent、時間幅と境界を持つ操作はSpan、その操作全体の性質はSpan属性、という使い分けも意味規約の考え方になる。Eventはトレース外でも発生できる。
