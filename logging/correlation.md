# 処理をつなぐID：同じものと、別の試行を見分ける

相関IDは、散らばった記録を探し直すための手掛かりである。IDを付ける前に、「何が同じなら同じIDか」を説明する。名前が同じでも、受信リクエスト、ジョブ全体、一回の試行では識別したい範囲が違う。

## 非同期処理を一つの例で考える

説明用に、HTTPでジョブを受け付け、キューへ送り、ワーカーが再試行して完了する処理を考える。

- 受け付けた一回のHTTP呼び出しを探したいなら、その受信を識別するIDが役立つ
- キュー待ちや再試行を含むジョブ全体を探したいなら、ジョブを通じて変わらないIDが役立つ
- 何回目の実行が失敗したかを調べるなら、試行を区別する情報が要る
- どの処理がどの依存先を呼び、どこで時間を使ったかを見るなら、トレースの処理区間と関係が役立つ

すべてを一つのIDで済ませると、ジョブ全体は探せても再試行同士を区別しにくい。逆に試行ごとに全部変えると、同じジョブの続きだと分からなくなる。変えないものと変えるものを分けるのが設計の中心になる。

この区分は理解のための設計例であり、request ID・correlation ID・trace IDを必ず三種類独立に導入するという規格ではない。request IDとtrace IDが同じ範囲を表す構成もある。

## トレースは、一致するID以上の情報を持つ

trace IDは一つのトレースを束ね、span IDはその中の処理区間を識別する。親子関係と時刻・所要時間があって初めて、つながりや各区間の時間を読める。同じtrace IDが付いた文章の集合だけでは、処理の構造を十分には復元できない。

request IDやcorrelation IDは、対象システムの契約を確かめて読む。W3C Trace ContextはHTTPでトレース情報を伝える仕様であって、汎用request IDやcorrelation IDの寿命を一律に定めてはいない。一方、メッセージングの意味規約にはメッセージIDと会話IDの区別がある。「相関IDには標準が一切ない」という理解も広すぎる。

例えばOTelの `messaging.message.id` はメッセージシステム上の一件、`messaging.message.conversation_id` は会話のまとまりを指し、後者はCorrelation IDと呼ばれる場合がある。確認日時点ではいずれもDevelopmentの属性で、全アプリに共通する汎用ID設計ではない。

## IDは、境界を越えて初めて役立つ

HTTPヘッダーやキューメッセージでコンテキストを運び、受信側で取り出す必要がある。さらに、同じプロセス内でもスレッドや非同期タスクをまたいで現在の処理と対応しなければならない。ヘッダー形式が正しくても、ロガーが自動的に継承するとは限らない。

並行処理では、前のリクエストのIDが次のログへ混入するのも問題になる。入口、外部呼び出し、キュー投入と実行、終了時の解放を一続きに試す。外部サービス側の問い合わせIDがあるなら、自分の処理との対応を残すと調査の接点になる。ただしその値にも収集・共有の安全性確認が要る。

設計時には、各IDについて生成者、識別対象、引き継ぐ境界、再試行で変わるか、どこまで外へ渡すかを言葉にする。長時間処理では複数トレースを業務上のIDでつなぐ選択もある。これらは採用側の設計判断であり、ID名だけから自動的には決まらない。

## 受信したIDを信用する範囲

外部から届いた相関値は、利用者の本人性や権限、処理の成立を証明しない。認証・認可に使わず、不正な形式や長さ、収集量への影響を境界で扱う。W3C Trace Contextは `traceparent` と `tracestate` に個人識別情報や機微情報を入れることを禁止している。

W3Cの `traceparent` は、トレース全体の `trace-id` と、呼び出し側の操作を示す `parent-id` などを伝える。受信したparent IDを、受信側で新たに動いているspan自身のIDと取り違えない。また `sampled` は、そのトレースが確実に保存されたという通知ではない。

セキュアな入口でトレースを再開始する選択は仕様上認められるが、あらゆる境界で必ずIDを変えるという一律の要求ではない。追跡性と信頼境界を合わせて判断する。

## ログへトレース情報を付けるとき

OTelの一般ログモデルではTraceIdとSpanIdは任意で、SpanIdがあるならTraceIdもあることが推奨される。トレース外のイベントやコンテキストのない記録に、存在しないIDを作って「つながった」ことにしない。

非OTLPのJSONログへの互換性規約では、`trace_id`・`span_id` の小文字十六進表現と、`trace_flags` の表現が示され、JSONのトップレベルへの配置が推奨される。この三欄も任意である。これは既存形式との橋渡しであり、任意のrequest IDをtrace IDへ改名する根拠ではない。実装時は採用する仕様の長さ・値の制約も検査する。

### 設計を確かめる小さな問い

再試行後の成功ログから、最初の失敗と受信記録へ戻れるだろうか。別のジョブが同時に動いても混ざらないだろうか。IDがない記録は「単独の出来事」なのか「伝播の失敗」なのか説明できるだろうか。この三つをたどると、IDを持っているだけの設計と、実際に追える設計の違いが見える。
