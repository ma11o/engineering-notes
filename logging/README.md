# ログ設計を理解する

ログ設計とは、将来調べたい出来事を、後から比較し、つなぎ、説明できる形で残すこと。出力箇所やログレベルを先に増やすより、「何を1件と数え、何が分かれば調査が進むか」から考える。

このノートは、ログを自分の言葉で説明し、設計やレビューで判断するための一般技術ノート。本文だけで考え方を追えるようにしている。

## 順に読む

0. [共通例1：レポート出力ジョブ](example.md) — 各章で使う一つの処理と、4つの場面の記録例
   - [共通例2：予約の問い合わせ](example-reservation.md) — 問い合わせを入口に、システムが何を判断して返したか、なぜその結果かを確かめる例
1. [ログ設計の原則](principles.md) — 調べたい問いから、必要な情報と比較対象を選ぶ
2. [イベントの設計](event-design.md) — 何が起きた1件かを決め、名前・属性・時点を揃える
3. [処理をつなぐID](correlation.md) — リクエスト、試行、トレース、業務上のまとまりを区別する
4. [レベル・結果・通知](severity-and-outcomes.md) — 例外やERRORから、処理の成否や人の対応を短絡しない
5. [情報を守る](security-and-privacy.md) — 調査に必要な文脈を、過剰な収集なしで残す
6. [記録の届き方と限界](reliability.md) — 欠損・サンプリング・保存方式を含めて、言えることを判断する
7. [設計をレビューする](review-checklist.md) — 代表的な場面をたどり、説明できない点を見つける

各章は主に共通例1の「正常終了」「再試行後の成功」「最終失敗」「途中停止」の4場面を使って説明する。自分の設計に当てはめるときも、一つの処理を選んで同じ4場面の記録を書き出すと進めやすい。問い合わせ対応が目的なら、共通例2のように「何を判断して返したか」の記録から考える。

## 根拠を確かめたいとき

章末から[リサーチ資料](research/README.md)へ進める。そこには書籍ノート、一次資料の該当箇所、仕様の状態、適用範囲、検証の限界を残している。出典を先に通読する必要はない。

## 全章に共通する前提

各章ではこの前提を繰り返さない。

- 仕様上の要求は、対象仕様と成熟度（Stable／Development）を明記する。それ以外の設計例や判断の進め方は、資料を踏まえた提案として読む
- 例のフィールド名・値・数値は説明用であり、OTel準拠のスキーマ、性能目標、許容値ではない
- 特定組織の採用規則、法令適合の判定、保存期間の基準を定めるものではない
- 外部資料の確認日は2026-10-07。実装言語・SDK・保存先を選んだ適合試験や実システムでの検証はしていない
