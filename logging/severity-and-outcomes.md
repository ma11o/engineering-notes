# ログレベルと処理結果を読み分ける

**要点**

- ログレベル・処理結果・通知は別々に決める。「例外が出た＝ERROR＝人を呼ぶ」ではない
- 各試行の成否と、操作全体の最終結果を別の記録にする
- 失敗率は同じ操作単位の分母で数え、通知は利用者への影響から決める

[共通例](example.md)の場面Bでは、PDF生成サービスへの呼び出しがタイムアウトし、再試行で成功した。最初の呼び出しは失敗したが、利用者のレポートはできた。ただし、時間がかかりすぎたなら、利用者への約束は守れなかったかもしれない。

この違いを説明するには、**どの操作の結果かを決め、その結果とログレベル、通知の必要性を分けて考える**。

- ログレベルは、記録した出来事の深刻さや性質を伝える
- 処理結果は、ある操作が期待した成果を満たしたかを表す
- 通知は、その状態を受けて誰かに行動を求める判断である

例外が起きたこと、操作が失敗したこと、ERRORを出すこと、人を呼ぶことは、一対一には対応しない。

## レベルを読むには操作の範囲が要る

よく使う四つのレベルを、OpenTelemetryのLogs Data Modelを足場に整理すると次のようになる。

| レベル | 意味の中心 |
| --- | --- |
| DEBUG | デバッグのための詳しい出来事 |
| INFO | 意味のある出来事が発生したという情報 |
| WARN | エラーとは区別される警告 |
| ERROR | エラーが生じた出来事 |

INFOの開始ログは成功の証拠にならない。ERRORの依存先ログも、利用者への最終結果を単独では説明しない。レベルだけでなく、何を、どの層が記録したかを見る。

ライブラリは呼び出し元へ失敗を返し、アプリケーションは代替手段で処理を完了することがある。OTelの例外ログのSeverityの推奨にも、アプリケーションが処理すると期待される例外をWARNとし、クライアントライブラリが再試行を使い切った失敗を一件のWARNで記録する例がある。「WARNなら復旧済み」「再試行が尽きたら必ずERROR」とは決められない。

資料の成熟度には注意したい。2026年10月7日の確認では、Logs Data Modelは**Stable**。一方、ここで使う例外ログのSeverity節と、後述する操作のエラー判定の推奨は**Development**だった。共通語彙と発展中の計装ガイダンスを区別し、後者を全アプリケーションの固定的な出力規則にしない。

成功の定義にも操作の目的が含まれる。存在確認の「見つからない」と、必須データの取得失敗は、同じ404でも意味が違う。「想定内」「catch済み」だけで成功とは決められず、HTTP 200でも必要な成果を返せていなければ目的は達成していない。

## 再試行と最終結果を読み分ける

場面Bには、失敗した試行が一件、成功した試行が一件、完了したジョブが一件ある。全部を「リクエスト」と呼ぶと、何を数えているか曖昧になる。

**悪い例**は、各層で同じ例外をERRORとして出し、その行数を利用者の失敗件数として数えることだ。一つの成功した要求が、複数の失敗に見えてしまう。反対に、最後の「成功」だけでは、なぜ遅かったかを説明できない。

**改善例**として、試行の詳細と全体の完了要約を別の出来事にする。

```text
DEBUG event=renderer.attempt_completed job_id=job-1025 attempt=1 outcome=failure
      error_code=renderer_timeout duration_ms=3000
DEBUG event=renderer.attempt_completed job_id=job-1025 attempt=2 outcome=success duration_ms=700
INFO  event=export.completed  job_id=job-1025 outcome=success attempt_count=2
      recovered=true duration_ms=3850
```

ここでは詳細調査用の試行ログをDEBUG、完了要約をINFOにした。大切なのは、**各試行の成否と、全体で何が成立したかが分かること**である。調査の目的によっては、試行の詳細より、要約の試行数や復旧情報だけで十分な場合もある。

OTelのエラー記録ガイダンスは、再試行などで完了した操作のspanやmetricに、途中の失敗をその操作の失敗として記録しないことを推奨する。途中の失敗を調べるログの一律禁止でも、失敗した試行を成功に書き換える指示でもない。

### 成功の条件が変われば判断も変わる

3850ミリ秒は、許容時間が10秒なら期限内だが、3秒なら遅延の目標を満たさない。時間が成功条件に含まれるなら、結果もその条件に沿って判断する。

グラフを省いた簡易版PDFを返す場合も、それで利用者の目的が満たせるかで結果は変わる。成果は満たしていても、試行回数や代替経路の利用が増えれば、依存先の劣化を示しているかもしれない。成功・失敗と併せて、所要時間や復旧への依存を観測したい。

## エラーの文章と分類を分ける

`Timeout while rendering job-1026 at 12:34:56`のような文章だけでは、IDや時刻が変わるたびに同じ問題が別の集団に割れてしまう。前の例の`error_code=renderer_timeout`は、同種の失敗をまとめるための安定した分類である。必要に応じ、例外の型、失敗した工程、依存先、実行バージョン、trace IDなどを加えると、集団の傾向から個別の調査へ進める。

書籍『Observability Engineering』でも、例外の型・メッセージ・スタックに加え、想定内かを区別する情報や、発生箇所を絞る安定した`exception.slug`を紹介している。属性名をまねるより、分類に個体IDや可変の値を混ぜないことが重要だ。

ただし、タイムアウトという分類だけでは、依存先の故障、ネットワーク、呼び出し側の負荷のどれが原因かは分からない。観測した事実と原因仮説を分ける。また、例外文やスタックには入力値や認証情報が混入し得る。自動取得した情報でも、無条件に保存してよいわけではない。

## 正常系があると失敗を説明できる

「タイムアウトが10件あった」だけでは、全体の1%なのか10%なのか分からない。書籍が重視する、異常な集団と通常の集団の比較にも、成功側の情報が必要になる。同じ操作名、バージョン、経路、所要時間などで比べられれば、失敗側だけに偏る条件を探せる。

例えば100件のレポート出力のうち、90件は初回で成功し（場面A）、8件は再試行で成功し（場面B）、2件は最終的に失敗した（場面C）とする。最終的な失敗率は2/100である。途中の失敗試行や、同じ失敗を別の層で記録したログを分子に加えてはいけない。

依存先への試行の失敗率を知りたいなら、失敗した試行を、成功も含む全試行で割る。どちらにも意味はあるが、答えている問いが違う。

成功ログだけを間引き、失敗ログを全件保存している場合も、残った行をそのまま割れば率が偏る。サンプリング、欠落、重複を確認し、集計用メトリクスを併用する場合も、同じ操作単位を数えているか確かめる。

## 人を呼ぶ条件を別に考える

「ERRORが一行でもあれば常に通知」では、再試行や重複記録で通知が増える一方、ERRORを出さない遅延や停滞を見逃し得る。

利用者操作の成功率や所要時間が、目標をどの程度・どの時間幅で外れているかを見る方法がある。Googleの『The Site Reliability Workbook』が扱う、サービスが満たす信頼性の目標（SLO）に基づく通知は、このように利用者が経験する信頼性に注目する。通知後にはログを使い、影響する集団や原因を調べる。

ただし、トラフィックが少なければ一件の失敗で率が大きく動く。データ損失などは、全体の率が小さくても一件から対応が必要になり得る。件数、影響、対応の必要性も見て、セキュリティや整合性の検知まで可用性SLOだけで満たせるとは考えない。

## 場面ごとの判断を表にする

共通例について、レベル・処理結果・通知を場面ごとに選んだ表が[共通例の判断表](example.md#レベル処理結果通知の判断表一例)にある。要点は次の三つである。

- 試行の失敗はワーカーが自分で回復する前提なのでDEBUG。ジョブとして成果を出せなかったときだけERRORにする
- 入力拒否はINFO、グラフを省いた簡易版での応答はWARNにし、処理結果は `rejected`・`success`（`degraded=true`）と別に書く
- 最終失敗は失敗率で通知し、ファイルとDB状態の食い違いのように自動で直らないものは一件でも対応を求める

自分の処理でも、場面を行に並べて「レベル／処理結果／通知」の三列を埋めると、判断の根拠を説明しやすい。

設計やレビューでは、レベルの名前より先に「何を一件とし、何が成立すれば成功か」を説明したい。そこから、試行と最終結果、正常な比較対象、通知の根拠を順にたどれば、必要な情報を具体化できる。
