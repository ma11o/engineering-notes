# 設計をレビューする：記録から一つの処理を説明できるか

フィールドの有無を数える前に、具体的な処理を一つ選び、その記録だけで何が説明できるかを確かめる。以下は学習・設計のための問いであり、採用済み規則や法令適合の判定表ではない。

## 1. 普通に成功した処理を説明する

- [ ] この記録は、受付、永続化、処理終了、応答完了のどの事実を表すか
- [ ] 受信処理と依存先呼び出しを区別し、何を一件と数えるか説明できるか
- [ ] 同じ操作の遅い例・失敗例と、結果、時間、バージョン、実行条件で比較できるか
- [ ] イベント名は種類を表し、個体IDなど変わる値は属性へ分かれているか
- [ ] 値の型・単位・不明や欠落の意味が、読み手によって変わらないか

ここで困るなら、まず[原則](principles.md)と[イベントの設計](event-design.md)へ戻る。成功した一件が説明できないまま、異常系だけ詳しくしても比較の土台ができない。

## 2. 一度失敗し、再試行で成功した処理を説明する

- [ ] ジョブ全体と各試行を区別し、同じ処理としてたどれるか
- [ ] HTTP、キュー、ワーカーの境界でIDが途切れず、別の並行処理と混ざらないか
- [ ] 下位の失敗と最終結果を混ぜず、失敗ログ件数を失敗操作数と誤読しないか
- [ ] 成功していても、時間悪化や再試行増加を調べられるか
- [ ] その層の責任と期待する影響からレベルを説明できるか。「例外だからERROR」だけになっていないか

IDの寿命は[相関](correlation.md)、結果とレベルは[レベル・結果・通知](severity-and-outcomes.md)で確認する。

## 3. 回復できず、利用者へ失敗を返した処理を説明する

- [ ] 失敗した操作・工程、安定したエラー分類、処理バージョン、関連IDが分かるか
- [ ] 期待した結果と期限を満たせなかったことを、例外の有無とは別に判断できるか
- [ ] 正常例を含む分母と集計の時間窓が分かるか。標本や欠損を無視していないか
- [ ] 人への通知が必要なら、誰が何を変えるための通知か説明できるか
- [ ] 一件単位で重要な事象を、全体の率だけで見落とさないか

例外がない失敗、想定内の入力拒否、代替経路での応答も加えると、条件が変わったときに判断を変えられるか確認できる。

## 4. 途中で止まり、完了記録が見つからない処理を説明する

- [ ] 開始や重要な中間状態から、どこまで進んだか分かるか
- [ ] 処理自体の停止と、記録の生成・転送・保存・検索の問題を区別する手掛かりがあるか
- [ ] サンプリング、遅延到着、保持期限でも同じ見え方にならないか
- [ ] キュー満杯、送信先停止、再試行期限、再起動、ディスク不足を想定したか
- [ ] 再送の重複と欠損をどう扱うか説明できるか。WALだけでゼロ損失と判断していないか
- [ ] 全件説明が必要な証跡なら、その範囲と保証を診断用データから分けて定義したか

「ログがないから起きなかった」と結論する前に、[記録の届き方と限界](reliability.md)を確かめる。

## 5. 調査できることと、残してよいことを両立させる

- [ ] 各属性の必要性を説明でき、本文の代わりに分類・件数・サイズなどを使えないか検討したか
- [ ] URL、ヘッダー、例外文、SQL、外部レスポンスにも秘密や個人情報が入り得ると考えたか
- [ ] 収集前からstdout、ファイル、Collector、保存先、バックアップまで、原文が残る場所を把握したか
- [ ] 属性を除去しても必要な出来事まで消えないか。ハッシュ化だけで匿名だと判断していないか
- [ ] 閲覧者、保持目的、期間、削除の扱いに根拠があるか
- [ ] 個別追跡用IDを残すことと、索引・メトリクスラベルへ載せることを分けたか

[情報保護](security-and-privacy.md)と[保存方式の限界](reliability.md)を合わせて確認する。

## 人が決めたことを、狭く自動検査する

意味が合意できたら、必須項目・型・単位・列挙値の契約テスト、伝播の統合テスト、合成機微データを用いた除去テスト、障害注入などへ落とせる。これらは本ノートの試験案で、CI実装や実システム検証は行っていない。

テストは「決めた型を守る」「代表場面でIDが渡る」といった条件を確かめられる。しかし、その情報で調査が十分か、未想定の機微情報がないか、通知閾値が適切かは、テストの成功だけでは決まらない。詳細な候補と限界は[試験対応表](research/review-test-matrix.md)にある。

最後に、調べたい問い、記録する単位と時点、代表的な結果、採用仕様、情報保護、欠損時に言えないことを短く説明してみる。説明できない部分が、次に決める設計事項になる。
