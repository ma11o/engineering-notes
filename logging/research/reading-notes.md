## 1. ログの目的: 後からどんな問いに答えたいか

### 本の記述

- Observabilityでは、既知の障害を検出するだけでなく、予想していなかったシステム状態を出力データから調査できることを重視する。熟練者の勘だけに依存せず、他のエンジニアも原因を調べられるかが重要になる。［第1章 pp.7–9］
- データの形が、後で答えられる問いを制約する。処理の文脈を保存しておけば、調査時点で集計軸や表示方法を選び直せる。［第5章 pp.81–84］
- ユーザー・業務の文脈は、技術的な異常を「誰に、どの操作で、どのような影響があったか」へ結び付ける。［第6章 pp.101–103］

### 解釈・実務への示唆

ログの価値は出力量ではなく、調査可能な問いで考えたい。例えば、次の問いを区別する。

- ある処理は成功したか。失敗・未完了なら、どの段階まで進んだか。
- 遅延や失敗は、特定の操作・バージョン・実行条件に偏っているか。
- 外部サービスの失敗か、自分のサービス内の失敗か。
- 同じ操作で成功しているケースと何が違うか。

障害調査用の記録と、監査・業務上の証跡は目的が異なる。後者の完全性を、サンプリングされる調査用ログで満たせると決めつけない（第10節も参照）。

## 2. 何を記録するか: 処理単位に文脈を集める

### 本の記述

本のいう **wide structured event** は、1つの処理単位について多数の属性を持つ構造化イベントである。行数を増やすという意味ではなく、関連する文脈を同じイベントに集めることで、複雑な結合をせずに調査できるようにする。［第5章 p.64、第6章 pp.85–86］

第6章の属性例を、用途別に整理すると次のようになる。これは必須項目一覧ではない。

| 調べたいこと | 本が挙げる情報の種類 | 出典 |
| --- | --- | --- |
| どこで、どのコードが動いたか | サービス・環境・インスタンス・リージョン、バージョン・ビルド・デプロイ情報 | pp.86–90 |
| 実行条件が違わないか | Feature flag、ランタイムや主要ライブラリのバージョン | pp.91–92 |
| 何の処理を実行したか | HTTPメソッド、ルート、応答ステータス、入出力サイズ | pp.93–96 |
| どこに時間・呼び出し回数を使ったか | 全体や主要工程の所要時間、DB・外部HTTPなどの呼び出し回数と累積時間 | pp.97–99 |
| 何が失敗したか | 失敗フラグ、例外の型・メッセージ・スタック、想定内か、安定したエラー識別子 | pp.99–101 |
| どの集団・条件に影響したか | ユーザーや組織の識別・分類、認証方式、レート制限、キャッシュの利用結果 | pp.101–105 |
| 実行時の状態に特徴がないか | 起動後の経過時間、CPU・メモリ等の補助的な状態 | pp.106–109 |
| 外部との接点を追えるか | 外部サービスの取引ID、接続先の種類、キュー投入時の情報 | pp.110–111 |

### 解釈・実務への示唆

考え方は「何をしたか + 結果 + 時間 + 実行条件 + 関連付け」で整理できる。ただし、収集候補と収集許可は別である。特にユーザーID、URL、ヘッダー、外部IDは第9節の検討が必要になる。

処理中に分かった情報を完了時の要約に集めれば、同じ処理の断片を毎回つなぎ直す手間が減る。一方、完了時にしか出力しない設計では、クラッシュ・停止・長時間の停滞を見落とし得る。開始・中間状態を残す必要性は、完了要約とは別に考える。

## 3. 構造化ログ: JSONにするだけでは足りない

### 本の記述

- 自由文から正規表現で値を抽出するより、キーと値に分けたデータの方が検索・集計しやすい。構造化ログと構造化イベントの違いは、保存先がそのデータを構造として扱うか、単なる文字列として扱うかにもある。［第5章 pp.69–72］
- 属性名・単位・意味の一貫性が必要。同じ論理値に複数のキーがあると調査を妨げる。［第7章 pp.126–127］
- 主要な処理を表すイベントを選別できるようにする。第6章の `main` は著者の一例であり、子のHTTP呼び出しまで混ぜるとリクエストのエラー率などを誤計算する。［第6章 p.110］

### 解釈・実務への示唆

- `message` の中に結果やIDを埋めるだけでなく、検索・比較する値を独立した属性として持たせる。
- 名前だけでなく、型・単位・欠落時の意味も揃える。例えば数値の `0`、値が不明、属性が存在しない状態を混同しない。
- 「受信リクエスト」「依存先への呼び出し」「リトライ試行」を同じ母集団として数えない。何を1件と数えるかが構造の一部になる。
- 書籍内でも属性名は例ごとに異なる。このノートの属性名は理解のための例であり、最新のOpenTelemetry仕様に準拠するスキーマとして転用するものではない。

## 4. event / event name: 発生したことと分類名を分ける

### 本の記述

- eventは文脈依存の用語。本では実用上、システム内の処理単位で起きたことを記録するデータとして扱う。［第5章 p.64］
- 検索できる一貫した `name` を付ける例、`event_name` で完了イベントを選び集計する例がある。［第5章 pp.76–77、81–82］
- spanやログの名前は、説明的で曖昧でなく、グループ化しやすいものにする。IDや可変のURL要素を名前に入れず属性へ分離する。dot notationと複数語のsnake caseについても述べる。［第7章 p.126］

### 解釈・実務への示唆

event nameは「この1件の固有名」ではなく「どの種類の出来事か」を識別するものとして考えると扱いやすい。

例えば、独自の説明用例として `job.completed` という種類と、`job_id`・`outcome`・`duration_ms` という値を分けられる。`job.98765.completed` のように個体IDを名前に混ぜると、同種のイベントを集計しにくい。

ただし、`completed` が「成功」を意味するのか「成否によらず終了」を意味するのかは別途定義が必要。命名規則より先に、発生条件と記録単位を明確にする。

ここで扱う観測用eventは、イベント駆動システムの業務イベント、配信保証のあるメッセージ、イベントソーシングの正本と同一ではない。また、書籍の一般的なeventという語と、特定APIのSpan Eventなどを無条件に同一視しない。

## 5. request ID / correlation ID / trace ID

### 本の記述

| 識別子 | 本での役割 | 出典 |
| --- | --- | --- |
| request ID | 並行するリクエストのログを区別し、1つの操作に属する記録を取り出す。プラットフォーム由来のリクエストIDも属性候補になる | 第5章 pp.71–72、第6章 p.93 |
| trace ID | 同じトレースを構成するspanを関連付ける | 第5章 pp.75–80 |
| span ID / parent ID | 処理区間を識別し、親子関係を復元する。時刻・所要時間と合わせて処理のつながりを表す | 第5章 pp.75–80 |
| correlation ID | 非同期パイプラインや長時間処理で、複数のトレースにまたがる論理的な取引・処理を関連付ける例がある | 第7章 pp.119–122 |

HTTPだけでなく、キューなどのメッセージにコンテキストを載せ、受信側で取り出す。プロセス間の伝播と、スレッド・コルーチン等をまたぐプロセス内の伝播の双方が必要になる。［第7章 pp.115–116、119–120］

### 解釈・実務への示唆

上表は本の例に沿った区別であり、IDの名前だけで識別範囲は保証されない。後で設計するときは、次を明らかにしたい。

- 1回のHTTP呼び出し、ジョブの1試行、複数試行を含む業務処理のどれを識別しているか。
- どこで生成し、どの境界で引き継ぎ、どこで新しく発行するか。
- リトライでは何が同じで何が変わるか。業務単位のIDと試行単位のIDを混同しないか。
- ログとトレースを同じIDから検索できるか。外部サービス側のIDとの対応が残るか。

request IDとtrace IDが同じ範囲を表す構成もあり得るため、3種類を必ず独立に導入するという意味ではない。IDを付けるだけでは親子関係や所要時間は復元できず、同じIDを持つことだけで因果関係が証明されるわけでもない。

## 6. ログレベルの使い分け

### 本の記述と限界

ログにseverityが含まれることには触れるが、今回確認した関連箇所には、DEBUG / INFO / WARN / ERROR等を網羅する実務上の判断表は見当たらない。エラーについては、処理の失敗、例外の型、想定内かどうか等を属性で表現している。［第5章 p.68、第6章 pp.99–101］

### 解釈・実務への示唆（本の規約ではない）

ログレベルは詳しさや深刻さを表す分類であり、業務上の結果を完全には表さない。使い分けを考えるための仮の整理は次のとおり（以下、仮のレベル表と呼ぶ）。

| レベル | 意味を検討する際の出発点 |
| --- | --- |
| DEBUG | 詳細な調査のための情報。出力量や常時保存の必要性を検討する |
| INFO | 通常の処理結果や意味のある進行・状態変化 |
| WARN | 回復や継続はできたが、劣化・異常な条件として把握したい出来事 |
| ERROR | 期待した処理を完了できなかった出来事 |

これは採用する運用規則ではない。例えば入力拒否、リトライ後の成功、外部障害時の代替動作は、例外の発生やHTTPステータスだけで一律に分類できない。結果・回復状況・影響とレベルを分けて考える必要がある。

また、ERRORが1件出たことと即時通知が必要なことは同義ではない。通知条件はレベルとは別に決める（[レベル・結果・通知](../severity-and-outcomes.md)）。

## 7. エラー時に残す情報

### 本の記述

失敗した処理には、例外の型・メッセージ・スタックトレース等の属性を付ける。第6章では、想定内の例外かを区別する情報と、コード内の発生箇所を検索できる安定した `exception.slug` も紹介している。slugは動的な値ではなく、集計可能な固定の識別子として使う。［第6章 pp.99–101、表6-14］

### 解釈・実務への示唆

「エラー文がある」だけでは、何が失敗したのか判断できない。次の組み合わせが調査に役立つと考えられる。

- 失敗した操作・工程と、その処理全体の結果。
- 安定したエラー分類、発生箇所を絞る情報、例外の型。
- 関連するrequest / trace / job等のID、サービスと実行バージョン。
- 依存先の種類、失敗までの時間、試行回数や最終的な回復結果。

後半の試行・回復情報は本の表の転載ではなく、処理の文脈という考え方からの補足。エラーメッセージには入力値や外部レスポンスが混入し得るため、「例外だから安全」とは扱わない。

同じ失敗を各層で繰り返し記録すると、発生件数とログ件数がずれる。低レベルの失敗と、呼び出し元の最終的な失敗を区別できる粒度・関連付けが論点になる。

## 8. 正常系・状態遷移のログ

### 本の記述

- 正常な集団と異常な集団を、共通する属性で比較する分析を重視する。［第8章 pp.138–141］
- 意味のある状態変化や、失敗し得る業務トランザクションはspan化の候補になる。全関数をspanにすることは勧めていない。［第7章 pp.116–118］
- 長時間ジョブでは、中間状態をログやメトリクスで示す方法、終了時に成功・失敗の詳細を要約する方法を説明する。既存spanを繰り返し更新する方法は、多くの保存先で扱えないとして推奨していない。［第7章 pp.121–122］

### 解釈・実務への示唆

失敗だけを記録すると、成功との比較や全体に対する失敗の割合が分からない。正常系にも、処理結果と比較に使える文脈が必要になる。

状態遷移については、例えば受付・開始・完了・失敗・中断のどれを区別したいかを考える。その際の候補は、処理識別子、前後の状態、工程、試行、経過時間、結果である。これは独自の整理であり、本が定める状態遷移スキーマではない。

さらに、DB上の状態変更を記録するなら「変更を試みた」「コミットされた」「利用者への応答が完了した」は異なる事実である。どの時点の記録か曖昧だと、ログ上は成功なのに状態が変わっていない、といった誤読が起きる。

完了ログがない理由も、未完了、プロセス停止、収集障害、保存期間切れ、サンプリングなど複数ある。「ログがない＝処理されなかった」とは断定できない。

## 9. 機微情報・PII・医療情報

### 本の記述

- ユーザー識別子がメールアドレス等の場合、外部サービスにPIIを送る組織の方針を考慮する。［第6章 p.102］
- SDKとCollectorでのフィルタ、属性のallowlist、変換処理など、多層で利用者情報を保護する。安定したハッシュによる関連付けにも言及する。［第7章 p.127］
- パイプラインでのPIIの除去に加え、アクセス・保存期間・データ所在地の制御を扱う。［第16章 pp.296–297］
- 識別子とセキュリティの関係を述べ、一方向ハッシュでも相関分析を維持できると説明する。［第31章 p.561］

### 解釈・実務への示唆と留保

**広い文脈を残すことは、入力・出力の本文を丸ごと残すことではない。** 本の属性例にはURLのクエリ、ユーザー情報等が含まれるが、記載されていることを収集許可と解釈しない。

医療情報について、今回読んだ箇所から具体的な記録可否や保存要件を確定することはできない。このノートでは法制度上の結論や業務上のルールを定めず、次の検討点までに留める。

- 氏名、連絡先、患者を識別する値、診療・処方などの本文、自由入力は、観測に必要な情報と分けて検討する。
- URL、SQL、例外文、ヘッダー、外部レスポンスにも機微情報や認証情報が入り得る。構造化しただけでは防げない。
- 本文ではなく件数・サイズ・所要時間・結果分類等で問いに答えられないかを考える。
- アプリ側で出さない対策と、収集経路で除去する対策の両方を考える。後段で消しても、それ以前の出力先に残る可能性がある。
- 内部IDや安定したハッシュでも、他の情報との照合・推測・追跡が可能な場合がある。**ハッシュ化したから匿名化済み・制約なし、とは判断しない。**

書籍p.127の「ハッシュ」と内部APIによる逆引き、p.561の一方向変換に関する説明は、実装・管理の前提を補って読む必要がある。ハッシュそのものの逆変換と、管理された対応表による照合は別物である。具体的な方式、アクセス権限、保存期間は採用時に別途決める。

## 10. メトリクス・トレースとの役割分担

### 本の記述

第5章は同じ構造化イベントから複数のビューを作る考え方を示す。一方、第7章では目的に応じた複数シグナルの利用も説明している。両者を合わせて読む。［第5章 pp.65–68、81–84、第7章 pp.118–126］

| シグナル | 本が示す主な役割・特性 | 注意点 |
| --- | --- | --- |
| メトリクス | 全体傾向、低コストの長期保存、素早い通知 | 事前集約で失った個別の文脈は復元できない。個別IDなど高カーディナリティ属性を無制限に付けない |
| トレース | 処理間のつながり、依存関係、各区間の時間と文脈 | コンテキスト伝播と意味のあるspan境界が必要。粒度が細かすぎても大きすぎても調査しにくい |
| ログ・イベント | 個々の出来事、途中経過、まれな事象、証跡など目的に合う詳細 | 相関情報がない断片の集積では、全体像の再構築が難しい |

課金等の重要なイベントには独立した経路が有用な場合がある。［第7章 p.125］HTTP処理では、トレースに加えてヒストグラムを出し、トレースがサンプリングされても集計・通知を支える例も示す。［第7章 pp.118、125］

リクエスト処理時にCPU等をイベントへ付ける方法は、調査の補助にはなるが、リクエストが来たときにしか観測されない。本はその値を通常の定期メトリクスと同じものとして通知に使うことを勧めていない。［第6章 pp.107–108］

### 解釈・実務への示唆

「全体の変化を知る → 条件で絞る → 個別処理を追う」と行き来できることが大切である。全情報をすべてのシグナルへ複製することとは違う。

観測イベントから集計する場合も、記録対象・欠損・サンプリングによって意味が変わる。第15章は採取率を記録し、件数や合計を重み付けする例と、トレース全体で一貫した採取判断を説明する。［第15章 pp.279–283］

これは母集団の実件数を常に正確に復元できるという保証ではない。偏った採取や失われた少数事例、分位点の扱いは別問題である。監査等の完全な記録と、調査用の標本を同じ保証で扱わない。

## 11. 障害調査で追いやすいログ

### 本の記述

第8章の分析ループは、症状を確認し、異常な集団と通常の集団を比較し、属性で絞り、仮説を検証して繰り返す方法である。相関と因果を混同しないことも指摘している。［第8章 pp.138–141］

### 解釈・実務への示唆

追跡しやすさは、次の往復ができるかで考えられる。

1. 時間帯・サービス・操作から、対象の母集団を選ぶ。
2. 結果・所要時間・バージョン・実行条件で、偏りを絞る。
3. request / trace等のIDから、個別の処理と依存先へ移る。
4. 失敗箇所や停滞工程を特定し、成功例との違いを確かめる。

そのため、時刻の意味・単位、処理単位、属性名、IDの範囲が揃っていることが重要になる。大量のログから人が文章を読み合わせる方法だけでは、この往復が難しい。

## 12. アンチパターンの整理

| パターン | なぜ調査を妨げるか | 根拠・位置づけ |
| --- | --- | --- |
| 自由文の正規表現検索だけに依存 | 文言変更に弱く、抽出・集計が複雑になる | 本: 第5章 pp.69–71 |
| JSONのmessageにすべてを詰める | フィールド単位で比較する利点を得られない | 解釈: 第5章 pp.70–72から |
| 処理の文脈が多数の断片に分散 | 1件の調査や横断比較で毎回再構築が必要 | 本: 第5章 p.84、第6章 pp.85、97–98 |
| event/span名に個体IDを含める | 同種の操作をグループ化しにくい | 本: 第7章 p.126 |
| IDが非同期境界で途切れる | 処理間のつながりを追えない | 解釈: 第7章 pp.115–122から |
| すべての関数・ループをspan化 | 情報量・費用が増え、意味のある処理が埋もれる | 本: 第7章 pp.116–118 |
| エラーだけを残す | 正常な比較対象や成功を含む母数が分からない | 解釈: 第8章 pp.139–141から |
| 親リクエストと子呼び出しを混ぜて集計 | 件数や失敗率の意味が変わる | 本: 第6章 p.110 |
| 属性名・型・単位の意味が不統一 | 検索漏れや誤集計を引き起こす | 本: 第7章 pp.126–127。型・欠損の詳細は本ノートの補足 |
| サンプリング後の件数を実件数とみなす | 頻度・率を誤認する | 本: 第7章 p.126、第15章 p.278、pp.281–283 |
| 完了記録だけで停滞・中断まで判断 | 完了しなかった処理の証拠が不足する | 解釈: 第7章 pp.121–122から |
| リクエスト本文や例外文を無条件で保存 | 必要以上の機微情報を残し得る | 解釈: 第7章 p.127、第16章 pp.296–297から |
| ハッシュ化したIDを無条件で安全とみなす | 関連付け・推測可能性や管理条件を見落とす | 本の説明に対する留保: 第9節参照 |

## 13. 実務と照合するときの問い

自分のシステムに当てはめるときに確かめたい問い。特定システムについての指摘ではない。

1. **調査の入口**: 最近困った調査で、答えたかった問いは何か。どの情報が足りなかったか。
2. **処理単位と結果**: 何を1件と数えるか。受付・永続化・処理完了・応答完了を区別する必要があるか。
3. **相関**: 現在のIDは何を識別するか。サービス間・キュー・リトライ・外部連携を越えて追えるか。
4. **比較可能性**: 正常と異常を同じ属性で比べられるか。ルート、バージョン、結果、時間が検索・集計できるか。
5. **エラーの意味**: 想定内の拒否、回復した失敗、最終的な失敗を区別できるか。重複記録で件数を誤読しないか。
6. **情報の境界**: 機微情報が入り得る箇所はどこか。調査目的を満たす代替属性は何か。閲覧権限・保存先・保存期間はどうなっているか。
7. **収集の前提**: 欠損・サンプリング・出力レベルによって、見えなくなる事象や集計の偏りはないか。
8. **シグナルの接続**: メトリクスで見つけた異常から該当ログ・トレースへ移れるか。証跡として別の保証が必要な記録はあるか。
