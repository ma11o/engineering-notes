# 共通例2：予約の問い合わせを調べる

[共通例1（レポート出力ジョブ）](example.md)は、処理が成功したか、なぜ遅い・失敗したかを追う例だった。この例では、利用者からの問い合わせを入口に、**その時点でシステムが何を判断して返したか、なぜその結果になったか**を確かめる。

この例も説明用に作ったもので、書籍 *Observability Engineering* の事例ではない。書籍の考え方のうち、利用者や組織の属性を処理の記録に加えること（第6章 pp.101–103）と、バージョンや機能フラグで集団を比べること（第6章 pp.89–92、第8章 pp.138–141）を使っている。

## 問い合わせと処理の流れ

> 「10月10日は予約できる条件なのに、画面で選べなかった」

利用者は次の順に操作する。

1. ログインする
2. 画面が **予約可能日API** を呼び、施設と月を指定して予約できる日の一覧を受け取る
3. 画面が一覧を表示し、利用者が日付を選ぶ
4. 予約内容を確認する
5. **予約登録API** が条件を確かめ、予約を登録するか拒否する

記録はサーバー（API）側だけで出す。画面での表示や日付の選択は記録しない。そのため、APIの記録から分かるのは「何を返したか」「なぜそう判断したか」「登録のリクエストが来たか」までである。

## 使うIDと出来事

| ID | 何が同じなら同じ値か | 生成する場所 |
| --- | --- | --- |
| `session_id` | ログインしてからのブラウザのセッション | 認証時 |
| `reservation_flow_id` | 日付の取得から登録までの、一回の予約の流れ | 画面が予約画面を開いたときに発行し、各APIリクエストのヘッダーで送る |
| `request_id` | 一回のHTTP呼び出し | API |
| `user_ref` | 利用者。メールアドレスや患者番号ではなく、内部で発行した参照用ID | 認証時 |

`reservation_flow_id` は、[共通例1](example.md)の `job_id` に当たる。複数のリクエストをまたいで変わらないので、一回の予約の流れをまとめて取り出せる。画面側でログを出さなくても、IDを発行してヘッダーに載せるだけでよい。

| 出来事（`event`） | いつ出すか | 記録する主な値 |
| --- | --- | --- |
| `reservation.availability.evaluated` | 予約可能日APIが判定を終え、応答を返す直前 | 判定の入力、予約可能日、予約できない日とその理由、`rule_version`、`evaluated_at` |
| `reservation.created` | 予約登録APIがDBへコミットした後 | `reservation_date`、`rule_version` |
| `reservation.rejected` | 予約登録APIが登録を拒否したとき | `reservation_date`、`reason_code`、`rule_version` |

各APIのリクエスト記録には、`user_agent` から取り出したブラウザの種類（`browser`）も残す。

## 判断の証跡：なぜその結果になったか

問い合わせに答えるには、返した日付の一覧だけでは足りない。「10月10日が入っていない」と分かっても、**なぜ入らなかったか**が分からなければ、利用者に説明できず、判定が正しかったかも確かめられない。

そこで、予約可能日APIは判定を終えた時点で、次の記録を一件出す。

```json
{
  "event": "reservation.availability.evaluated",
  "request_id": "req-51c0",
  "reservation_flow_id": "rf-3301",
  "user_ref": "u-7d41",
  "facility_id": "f-12",
  "requested_month": "2026-10",
  "user_segment": "general",
  "evaluated_at": "2026-10-03T09:12:44Z",
  "rule_version": "v2",
  "available_dates": ["2026-10-12", "2026-10-15", "2026-10-19"],
  "unavailable_by_reason": {
    "closed_day": ["2026-10-05", "2026-10-26"],
    "slot_full": ["2026-10-10", "2026-10-11"],
    "outside_booking_window": ["2026-10-01", "2026-10-02"]
  }
}
```

この一件には、判断を説明するための四つの要素が入っている。

- **判断の入力**：施設（`facility_id`）、対象の月（`requested_month`）、判定を左右する利用者の区分（`user_segment`）。区分は「一般」「会員」のような分類にとどめ、氏名や病歴などは入れない
- **判断の時点**：判定した時刻（`evaluated_at`）。受付期間や空き枠は時刻で変わるので、「いつの判定か」がないと後から説明できない
- **判断の根拠**：適用したルールのバージョン（`rule_version`）
- **判断の結果と理由**：予約可能日（`available_dates`）と、予約できない日を理由ごとにまとめたもの（`unavailable_by_reason`）。理由は `slot_full`（枠が埋まっていた）のような安定した分類で書く

設計時に決めておくことが二つある。

- **一つの日に複数の理由が当てはまるとき**：最初に当てはまったルールだけを書くのか、すべて書くのか。最初の一つだけなら、ルールを評価する順番も仕様として固定する
- **量の上限**：一か月分なら日付をすべて書けるが、範囲が広い処理では、理由ごとの件数と代表例に絞るなど上限を決める

レスポンス全文は残さない。問い合わせに答えるのに要る判定の要約だけを、この一件にまとめる。

## 5つの場面

以下では、共通する `session_id`・`user_ref` などを省略する。

### A. APIがその日を返していない

```text
INFO event=reservation.availability.evaluated reservation_flow_id=rf-3301
     requested_month=2026-10 evaluated_at=2026-10-03T09:12:44Z rule_version=v2
     available_dates=[2026-10-12,2026-10-15,2026-10-19]
     unavailable_by_reason={slot_full:[2026-10-10,2026-10-11], ...}
```

10月10日は `slot_full` に入っている。10月3日9時12分の判定の時点で、その日の枠は埋まっていた。問い合わせには「ご覧になった時点では10月10日の枠が埋まっていました」と事実で答えられる。

利用者が「条件を満たしているはず」と言う場合は、理由の分類から確かめる先が決まる。`outside_booking_window` なら受付期間の設定と判定時刻を、`user_segment` による除外なら利用者の区分が正しかったかを確かめる。

### B. APIは返したが、予約登録のリクエストが来ていない

```text
INFO event=reservation.availability.evaluated reservation_flow_id=rf-3302
     available_dates=[2026-10-10,2026-10-12,2026-10-15] rule_version=v2
（同じ reservation_flow_id の予約登録リクエストが見つからない）
```

APIは10月10日を返している。登録のリクエストが来ていない理由は、利用者が選ばなかったか、画面で選べなかったかのどちらかで、画面の操作を記録していないので、APIの記録だけではこれ以上分けられない。

問い合わせへの回答には、「APIは10月10日を予約可能として返していた」という確かめられた事実と、「画面で何が起きたかは記録がなく確かめられない」ことを分けて書く。同じ時期に画面の更新があったか、同じブラウザの利用者で登録まで進んだ割合が下がっていないか（場面D）を合わせて見る。

### C. 予約登録で拒否された

```text
INFO event=reservation.availability.evaluated reservation_flow_id=rf-3303
     evaluated_at=2026-10-03T09:12:44Z available_dates=[2026-10-10,2026-10-12]
INFO event=reservation.rejected reservation_flow_id=rf-3303
     reservation_date=2026-10-10 reason_code=slot_full rule_version=v2
```

一覧を返した時点では10月10日は空いていたが、登録の時点で枠が埋まっていた。一覧を返してから登録するまでの間に、ほかの人が予約したと考えられる。

拒否は業務上想定された結果なので、レベルはINFOにしている。処理結果は `rejected` で、失敗（`failure`）とは分けて数える。

### D. 特定のブラウザだけ選択に失敗する

一件だけでは原因を決められないので、集団を比べる。予約可能日を返した予約の流れのうち、予約登録のリクエストまで進んだ割合を、APIの記録に残した `browser` 別に並べる。特定のブラウザだけ割合が低ければ、画面の不具合を疑う。

これは[ログ設計の原則](principles.md)の「一件を追う」と「集団を比べる」の往復である。画面の操作を記録していなくても、APIに届いたリクエストの比較で仮説を確かめられる。

### E. 新しいルールのバージョンだけ問題が起きる

`rule_version` 別に、予約可能日として返した日数や、`unavailable_by_reason` の理由ごとの日数を比べる。`v3` に切り替えた後だけ `outside_booking_window` が急に増えていれば、受付期間のルール変更を疑う。判断の証跡に理由とバージョンを入れておいたことで、この比較ができる。

## 問い合わせから調べる手順

1. 問い合わせの利用者と日時から `user_ref` と `session_id` を特定する
2. その時間帯の `reservation.availability.evaluated` を探し、`reservation_flow_id` を得る
3. 問い合わせの日付が、予約可能日に入っていたか、どの理由で外れていたかを見る（場面A）
4. 同じ `reservation_flow_id` の予約登録の記録を見る（場面B・C）
5. 一件で決められなければ、D・Eのように同じ条件の集団と比べる
6. 回答には、確かめた事実と、記録がなく確かめられなかったことを分けて書く

## 共通例1との違い

| 観点 | 共通例1（レポート出力） | 共通例2（予約の問い合わせ） |
| --- | --- | --- |
| 調べる入口 | 遅延や失敗の検知 | 利用者からの問い合わせ |
| 知りたいこと | 処理が成功したか、なぜ遅い・失敗したか | システムが何を判断して返したか、なぜその結果か |
| 一連の処理をまとめるID | `job_id` | `reservation_flow_id` |
| 中心になる記録 | 処理の要約（`export.completed`） | 判断の証跡（`reservation.availability.evaluated`） |

イベント名・フィールド名・理由の分類は、本ノート独自の提案である。
